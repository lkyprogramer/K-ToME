## 3. Architecture Target

The runtime target is a client-only presentation layer:

```text
RenderSnapshot / map topology
 -> client derives RoomPresentationPlan
 -> selected RoomArtPlate asset is drawn in the map stage
 -> interaction grid and gameplay overlays draw above the plate
 -> actors / loot / telegraphs / cursor / selection remain runtime-owned
```

Topology clipping contract:

Current implementation gap:

The active implementation draws one family-level room-art plate into the
axis-aligned bounds of visible map materials. It does not yet implement a
polygonal playable-room mask, 9-patch decomposition, door/wall alignment or
deterministic room-signature UV anchoring. This is acceptable only for the
current proof-slice evidence. It is not sufficient evidence that Direction A
generalizes to arbitrary procedural room shapes.

Target contract:

1. The presentation plan should derive its playable-room mask from the existing
   runtime visible material topology, such as the same visible floor/cell set
   already used by `TileRenderer` for visible-room material decisions.
2. The mask must be derived from current render data, viewport and deterministic
   room signature. It must not store or invent a second map truth.
3. Plate UV/placement should be anchored by world coordinates or deterministic
   room signature so camera movement does not cause texture swimming.
4. A full-room candidate may include baked wall mass, floor slabs, door mouths,
   warm light and dark corners. Runtime clipping still owns where the plate is
   visible inside the actual demo room.
5. A material-only floor plate can be used as a technical smoke candidate, but
   it is not the default final art direction unless evidence proves the
   narrower route solves the blocker better than a full authored room plate.

Generalization failure modes to check before broader closure:

1. bbox stretch: a fixed authored room plate deforms under very wide, tall or
   compact room bounds.
2. composition mismatch: baked wall mass, door mouths, light pools or dark
   corners land on playable cells that do not match the actual room topology.
3. visibility swimming: changing visible cells changes the bounds and causes
   the plate to resize, shift or recompose during exploration.
4. topology overfit: a candidate passes the fixed proof crop but fails L-shape,
   cross-room, narrow corridor, offset room or multi-room visible layouts.

D9 real-procgen ROI gate:

1. Sample 20-50 seed/floor/profession combinations from the same playable
   procgen path, not only curated demo probe seeds.
2. For each visible room sample, record `tileset`, bounds, visible cell count,
   `fillPermille`, `aspectPermille`, connected component count and topology
   decision.
3. Report aggregate `FULL_PLATE_SAFE` hit rate and each `TOPOLOGY_RISK_*`
   reason. Use `RoomArtPlateTopologyContract` metrics as the source of truth
   unless a separate implementation contract explicitly changes it.
4. The decision packet must compare the hit rate against Direction A cost: one
   authored full-room plate, one dedicated topology source and the hybrid
   composition grammar per family.
5. If plate-safe hit rate is too low to justify broad authored-plate rollout,
   converge to hybrid-first composition or stop Direction A expansion instead of
   tuning another source or alpha value.

Target render order:

1. room art plate, clipped/masked to the selected room presentation area
2. any retained semantic terrain or non-floor hazard material needed for rules
3. minimal retained wall/corridor transition treatment only when not baked well
   enough into the selected plate
4. runtime light/edge feather only where it improves readability without
   fighting baked art
5. restrained interaction grid for hover, selection, targeting, pathing and
   range feedback
6. actors, loot, telegraphs, cursor, combat feedback and selection overlays

Recommended production types:

1. `RoomPresentationPlan`
   - client-only, derived from viewport, visible room bounds and deterministic
     room signature
   - no `core` / `game` dependency in the opposite direction
2. `RoomArtPlateModel`
   - selected visual asset, map-stage rectangle, playable-room inset, overlay
     alpha budget and debug metadata
3. `RoomArtPlateCatalog`
   - client-only selector keyed by `tilesetKey`, optional biome/theme tags and
     deterministic room signature
   - returns no plate for unsupported families so they fall back to the existing
     tile renderer
4. `RoomArtPlateRenderer`
   - isolated drawing code, preferred over adding more private methods to
     `TileRenderer`
5. `RoomInteractionOverlay`
   - low-alpha grid/hover/path/range feedback above the plate

## 14. Rollback Plan

1. Review-only candidates need no runtime rollback.
2. If production resource promotion fails, remove the room plate key/manifest
   entry/resource file and restore the previous V48 map rendering path.
3. If runtime prototype fails readability, keep the selected plate as rejected
   evidence under `UI/review/...` and do not update golden baselines.
4. If old pass deletion causes regressions, restore only the specific retained
   interaction/marker pass needed for readability; do not restore the whole
   decorative stack without an agent-owned decision record.
5. Do not use `git reset --hard` as rollback. Use targeted patches and record
   the rollback in the iteration log.
