# K-ToME Dark UI Design Reference For Open Design

## 1. Status And Authority

This file is a repo-local reference for using Open Design style exploration against K-ToME dark UI/UX work.

It is intentionally **auxiliary only**. It can help critique layouts, generate visual alternatives, and keep PR04-PR07 design discussion consistent, but it is not an implementation contract.

Authority boundaries:

| Topic | Authority | This file may do | This file must not do |
| --- | --- | --- | --- |
| Product scope and redesign sequence | `UI/PLAN.md` | summarize design intent for review | change PR scope, gate order, or pipeline ownership |
| Dark UI style contract | `UI/ART_STYLE_BIBLE.md` | restate derived color/material/component guidance | redefine the style tag, core palette, sheet rules, or forbidden style |
| Sheet cell mapping | `UI/sprite-sheets/sheet-plan.yaml` | explain how UI design should respect mapped key families | define `sheetId`, `row`, `col`, `targetKey`, `outputName`, or raw sheet paths |
| Visual manifest truth | `assets-src/image/manifests/phase2-visual-manifest.json`; runtime copy generated by sync | remind designers to use manifest keys | invent manifest keys, raw output paths, fallback inventories, or runtime resource truth |
| Runtime UI behavior | `client` presentation/render/input code and PR docs | call out visual expectations to review | override typed snapshot, presenter, input, validation, or golden contracts |

If this file conflicts with any authority above, ignore this file and fix or revise it.

## 2.1 Original Design Requirements

This section restates the original redesign requirements from `UI/PLAN.md` and `UI/ART_STYLE_BIBLE.md` for Open Design review. It is a summary only; the source files remain authoritative.

### 2.1.1 Product Goal

The dark UI/UX redesign upgrades K-ToME's player-visible UI and visual resources into a unified dark Roguelike style while preserving the current Kotlin + libGDX + Tile rendering architecture.

Core product requirements:

1. Rework information architecture instead of only repainting old screens.
2. Iconify equipment, inventory, skills, items, status, quest, and major UI affordances.
3. Introduce an icon-first left navigation rail.
4. Turn the right side into a player panel for character state, equipment slots, inventory grid, and resource counts.
5. Keep a single bottom HUD for HP/stamina/experience, log, shortcut bar, and key hints.
6. Replace old player-visible visual resources so the new UI is not dragged down by old-style residue.
7. Keep the central map as the primary view, using dark frame, shadow, and boundary material to improve tactical focus.
8. Preserve keyboard-first interaction; do not introduce a D-pad in this redesign stage.

### 2.1.2 Authority And Non-Reset Rule

The style chain is:

```text
docs/2026-03-13-art-style-bible.md -> UI/ART_STYLE_BIBLE.md -> PR docs / sheet-plan / manifests / implementation
```

Rules:

1. `UI/ART_STYLE_BIBLE.md` is the dark UI/UX and sprite-sheet production style contract.
2. `docs/2026-03-13-art-style-bible.md` remains the parent world/art contract.
3. `ktome-dark-fantasy-sprite-ui-v1` is a dark UI/resource sub-epoch of the existing high-fantasy world, not a world reset.
4. If the dark UI direction conflicts with the parent world style, preserve the parent world first and adjust UI expression.
5. All new UI/visual prompts, sheet specs, cut reports, contact sheets, manifest patches, and coverage artifacts must record the style tag when they belong to this epoch.

### 2.1.3 Stable Scope Boundaries

The redesign must not quietly expand into gameplay or persistence work.

Stable boundaries:

1. Do not change gameplay rules as part of visual replacement work.
2. Do not change save, replay, or profile schema for the visual redesign itself.
3. Do not copy rule state into `client`; `client` consumes snapshot and manifest authority.
4. Do not treat images as mapping truth; `UI/sprite-sheets/sheet-plan.yaml` owns sheet cell to visual key mapping.
5. Canonical manifest comes first; runtime manifest is generated by sync.
6. Do not introduce atlas / region manifest schema during resource replacement PRs; PR07 only decides whether a later atlas PR is needed from evidence.
7. Every committed artifact, report, manual record, prompt index, manifest patch, or fixture must use repo-relative paths.

### 2.1.4 Required UI Surfaces

Open Design critique must not focus only on the in-run HUD. The final design surface includes:

1. home / main menu;
2. new run / player creation;
3. continue unavailable state;
4. validation entry and `ValidationSetupScreen`;
5. validation overlay and active content pack summaries;
6. in-run shell, central map, bottom HUD, log, and shortcut areas;
7. equipment, inventory, item tooltips, and inscription shop;
8. Talent Assign, active slot modal, and passive/detail variations;
9. status, quest, skill, profession, tree, fallback, missing, hidden, and debug visuals;
10. Look / Inspect;
11. world route;
12. stat assign;
13. reward / frontstage;
14. victory / defeat outcome;
15. loading, runtime error, and standalone `UiErrorScreen`;
16. settings / accessibility.

`UI/pr/screen-coverage-matrix.md` is the audit entry. By PR07, every Required or Conditional surface must have owner PR, focused test or golden/manual evidence, and packaged app or debug client whitebox evidence.

### 2.1.5 Visual Production Requirements

The original design goal is not "make prettier pictures." It is:

```text
Every small visual must be machine-cut accurately, mapped through manifest authority, and readable to players inside the dark UI.
```

Production rules:

1. Sprite sheets use fixed grids; no free placement.
2. Each cell contains exactly one subject.
3. No cross-cell subjects, merged cells, baked text, row/col labels, logos, or watermarks.
4. Icon, actor, and prop cells keep safe margins; portrait cells keep larger safe margins; tile ground/wall cells fill their cell.
5. Same sheet means consistent light direction, camera, outline weight, and density.
6. Contact-sheet QA must reject unclear boundaries, style drift, illegible subjects, and baked text.
7. Runtime readability is checked at the display sizes players actually see, especially `32x32`, `48x48`, and `64x64`.

### 2.1.6 Design Review Standard

When reviewing Open Design output, ask whether it supports the original redesign, not whether it is visually attractive in isolation.

The design must:

1. feel like one dark tactical Roguelike product across all screens;
2. keep dense operational UI instead of marketing or hero-page layout;
3. preserve gameplay readability over ornament;
4. use color as role language, not decoration;
5. keep status, quest, skill, item, profession, fallback, and debug families distinguishable;
6. expose disabled, focused, selected, learned, locked, warning, missing, and fallback states without relying only on color;
7. avoid old-style residue and cross-era collage;
8. avoid AI-slop signals such as fake text, impossible icon subjects, bad crops, random detail noise, and inconsistent perspective.

## 3. Open Design Usage

Allowed use:

1. Create design critiques for PR04-PR07 screens, including PR04-01 passive Talent Assign detail evidence.
2. Compare alternate compositions against K-ToME dark UI roles.
3. Prepare moodboards or reference notes for reviewer discussion.
4. Suggest component-state refinements before they are translated into PR docs or tests.
5. Identify visual anti-patterns early, before assets or renderer code are changed.

Disallowed use:

1. Do not treat Open Design output as `sheet-plan.yaml`.
2. Do not generate new manifest keys from Open Design labels.
3. Do not copy Open Design colors directly into runtime code unless the owning PR updates the real token/renderer contract.
4. Do not bake text, hotkeys, locale strings, numbers, or target keys into images.
5. Do not replace PR acceptance matrices, golden labels, manual records, or validation gates with visual notes from this file.

## 4. Color Roles

These roles mirror `UI/ART_STYLE_BIBLE.md`. Use them for design review language; implementation tokens remain owned by code and PR docs.

| Role | Hex | Design use | Notes |
| --- | --- | --- | --- |
| `void-black` | `#05070A` | main background, deep modal interior, map outside darkness | base darkness, not a full-screen flat fill without material |
| `charcoal-panel` | `#10151D` | panel body, sidebar surfaces, dense tool areas | default surface color |
| `iron-edge` | `#2B3542` | panel borders, slot rims, dividers | thin structural boundary |
| `cold-cyan` | `#1CB7C8` | focus edge, learnable affordance, active selection line | small-area highlight only |
| `ember-gold` | `#D99A2B` | titles, rare/resource emphasis, reserve state, confirmation accent | warm counterweight to cyan |
| `blood-red` | `#B64242` | danger, warning, HP loss, invalid destructive state | do not use for normal unavailable gray |
| `stamina-green` | `#52C989` | stamina, recovery, learned-active talent state | positive active gameplay state |
| `arcane-violet` | `#7B5CE1` | arcane, shadow, experience, magic rarity | accent, not global theme |
| `muted-text` | `#AEB5BF` | metadata, secondary labels, inactive detail rows | readable but quiet |
| `primary-text` | `#E7E1D3` | main labels and body copy | warm off-white, avoid pure white as default |

Talent state tones:

| State | Token | Color | Design use |
| --- | --- | --- | --- |
| `LOCKED` | `talent-locked` | `#59616C` | locked node, disabled prerequisite, inactive connector |
| `LEARNABLE` | `talent-learnable` | `#1CB7C8` | learnable node marker, focus affordance |
| `LEARNED_RESERVE` | `talent-reserve` | `#D99A2B` | reserve node, reserve action, held talent |
| `LEARNED_ACTIVE` | `talent-active` | `#52C989` | active learned node, equipped active confirmation |

Color discipline:

1. The UI should read dark first, material second, highlight third.
2. Cyan is a focus/edge language; it should not become the main background.
3. Gold is title/resource/reserve emphasis; it should not make every border look rare.
4. Red is reserved for danger or invalid state.
5. Purple is domain-specific for arcane/shadow/magic and must not dominate the UI.
6. State must not be conveyed by color alone; use marker, icon, text, position, or frame treatment as a second channel.

## 5. Spacing And Density

This section is design guidance for critique and mockups. Runtime layout remains owned by renderer code and PR contracts.

| Element | Guidance | Rationale |
| --- | --- | --- |
| Screen composition | dense but legible; no marketing hero layout | K-ToME is an operational roguelike UI, not a landing page |
| Outer panels | use one primary surface per modal/screen area | nested cards reduce tactical readability |
| Panel padding | compact inner padding, typically `12-20px` in mockups | keeps inventory, tree, log, and HUD information scannable |
| Column gap | visually stable gap, typically `16-24px` in mockups | separates panes without wasting space |
| Border weight | thin `1-2px` edges with material texture | forged-iron feel without noisy frames |
| Row height | stable across state changes | focus, icon, rank, and disabled state must not shift surrounding rows |
| Icon display | design around `32px`, `48px`, and `64px` use cases | source sheet cells are larger; runtime readability is smaller |
| Section headers | slightly tighter than rows, but still distinct | headers group content; they are not selectable rows |
| Footer strips | persistent and compact | navigation help and legends should not scroll away |
| Modal chrome | large surface, restrained ornaments | gothic material language without covering content |

Spacing rules:

1. Do not use oversized decorative cards for repeated operational rows.
2. Do not let selected/focused state change row height or push rank text.
3. Keep keyboard help, legend, and critical status visible at canonical evidence size.
4. Prefer dividers and tone contrast over large whitespace.
5. Treat source sheet safe margins separately from runtime UI spacing.

## 6. Component States

### 6.1 Panel And Modal

| State | Visual treatment |
| --- | --- |
| default | charcoal or void-black body, iron-edge border, low contrast inner texture |
| focused | restrained cyan edge or left strip, not full neon glow |
| selected | stronger cyan line or fill, still preserves text/icon state colors |
| disabled | muted-text and talent-locked gray; do not reduce opacity until unreadable |
| warning | blood-red or ember-gold depending on danger vs unmet condition |
| modal | heavier black iron frame, persistent title and footer areas |

### 6.2 Slots And Inventory Cells

| State | Visual treatment |
| --- | --- |
| empty | dark hollow center, iron rim, clear placeholder silhouette if needed |
| equipped | ember-gold inner accent, not full golden fill |
| selected | cyan focus edge plus stable slot dimensions |
| invalid target | red warning edge or sigil, not just gray |
| pending replacement | separate focus and replacement affordance; do not merge into one ambiguous glow |

### 6.3 Talent Rows

| State | Marker | Tone | Visual rule |
| --- | --- | --- | --- |
| locked | `[x]` | locked gray | readable but subdued |
| learnable | `[+]` | cyan | state marker remains visible even when row is focused |
| learned active | `[*]` | green | learned state must not be confused with focus |
| learned reserve | `[r]` | ember-gold | reserve is a state, not just an action hint |
| pending allocation | overlay/secondary accent | rare or pending accent | pending is not a fifth talent state |

Talent row grammar for design review:

```text
indent + connector + state marker + skill icon + talent name + rank
```

The renderer/presenter owns the exact model. Open Design mockups should preserve the grammar but must not infer rules from visual position alone.

### 6.4 Buttons And Keycaps

Design keycaps as small command chips:

```text
Enter Learn
R Reserve
Esc Back
```

Rules:

1. A keycap is not a large CTA button.
2. Use stable width and compact labels.
3. The command text must follow runtime input truth and localization.
4. Do not draw keyboard shortcuts into source art.

### 6.5 Text And Icons

Text:

1. Main text uses warm off-white.
2. Secondary metadata uses muted gray.
3. Titles use ember-gold.
4. Avoid pure white blocks and high-saturation paragraphs.

Icons:

1. Single subject.
2. Strong silhouette at `32x32`.
3. No letters, numbers, watermarks, UI labels, or baked hotkeys.
4. No merged subjects across sprite cells.
5. Maintain consistent light direction and outline weight within a sheet.

## 7. Material Language

Positive material language:

1. forged iron edges
2. worn stone centers
3. old leather backing
4. brass rivets and nicks
5. ember scratches and warm title glints
6. cold cyan rim light for focus only
7. dungeon grit and soot

Use material to clarify hierarchy:

| Surface | Material cue |
| --- | --- |
| primary modal | heavy black iron frame, stone panel body |
| sidebar/list | flatter charcoal surface with thin separators |
| selected row | cyan strip or shallow cyan fill |
| tooltip | charcoal stone center with thin iron border |
| action slot | dark hollow center, readable icon subject |
| rare/important frame | small ember or brass accent |

## 8. Anti-Patterns

Visual anti-patterns:

1. sci-fi HUD grids
2. neon cyberpunk glow fields
3. mobile gacha shine
4. anime/chibi faces
5. glossy plastic buttons
6. bright glassmorphism
7. pure flat office icons
8. beige parchment theme replacing dark fantasy
9. one-note purple/blue UI
10. decorative cards inside cards
11. large gradient backgrounds without material purpose
12. text, numbers, hotkeys, labels, logos, or watermarks baked into images

Implementation/process anti-patterns:

1. Open Design output becomes a manifest key list.
2. A mockup path becomes a runtime raw asset path.
3. A color sampled from a generated image bypasses `UI/ART_STYLE_BIBLE.md` and renderer tokens.
4. Renderer derives gameplay state from color, icon key, localized text, or row index.
5. A design note changes `sheet-plan.yaml` mapping without the sheet-plan owner path.
6. A fallback icon is treated as finished evidence without residual risk and owner.
7. A new component state appears in design without a typed state owner.
8. A visual polish request silently expands PR scope or gate ownership.

## 10. Review Questions

Before accepting an Open Design suggestion, answer:

1. Does it preserve `ktome-dark-fantasy-sprite-ui-v1`?
2. Does it keep UI operational and dense rather than promotional?
3. Does it use color as role language, not decoration?
4. Does it avoid baked text and raw path assumptions?
5. Does it require a new typed state, manifest key, sheet cell, or validation gate?
6. If yes, is that change routed to the real authority file instead of this reference?
7. Can the design survive runtime localization and smaller display sizes?
8. Does it keep gameplay state sourced from snapshot/presenter contracts?

## 11. One-Line Rule

Open Design may help K-ToME see the UI more clearly; it must not become a second source of truth for scope, state, sheet mapping, manifest keys, or runtime behavior.
