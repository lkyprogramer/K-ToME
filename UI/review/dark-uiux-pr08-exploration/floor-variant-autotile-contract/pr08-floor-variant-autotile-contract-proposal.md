# PR-08 Floor Variant/Autotile Contract Proposal

> Date: 2026-05-28
> Status: `slice-a-b-runtime-ab-executed-u04-not-final`
> Scope: Dark UI/UX PR-08 map-stage floor structure

2026-05-28 update: Slice A/B was executed with the U04 generated floor variant
family. The manifest-owned family, preload expansion and deterministic runtime
selection path passed focused validation and produced golden evidence. The
visual verdict is not final director acceptance: U04 proves the resource-family
route is technically sound, but the runtime crop still reads grid-first because
constant lattice/contact hierarchy and wall crown/side language dominate the
room read.

## Direct Conclusion

The next PR-08 map iteration should promote floor variation into an explicit
resource contract. The recommended path is a small, manifest-owned floor
variant family for `tileset.ruins.ground_01`, not another single-tile reroll and
not a full wall autotile system yet.

The current blocker is no longer just asset polish. The latest AG/AH/AI
resource sprint and the room-scale material-field pass both show the same
problem: a single repeated 128px floor cell keeps the runtime crop grid-first
even when the compositor improves room mass and marker readability.

## Recommended Contract

Add a four-entry floor variant family, with the existing base key kept as the
fallback and first family member:

| Role | Visual key | Output |
| --- | --- | --- |
| Base/fallback | `tileset.ruins.ground_01` | `dark-v1/tiles/tileset_ruins_ground_01.png` |
| Variant 1 | `tileset.ruins.ground_01.variant_1` | `dark-v1/tiles/tileset_ruins_ground_01_variant_1.png` |
| Variant 2 | `tileset.ruins.ground_01.variant_2` | `dark-v1/tiles/tileset_ruins_ground_01_variant_2.png` |
| Variant 3 | `tileset.ruins.ground_01.variant_3` | `dark-v1/tiles/tileset_ruins_ground_01_variant_3.png` |

The family should be authoritative in existing resource files only:

1. `UI/sprite-sheets/sheet-plan.yaml` owns the added cells and output paths.
2. `UI/sprite-sheets/key-registry.yaml` owns owner, fallback, consumer and
   consumerTest metadata for each new key.
3. `UI/sprite-sheets/owner-contracts/pr08-owner-keys.yaml` expands
   `r02-ui-demo-ruins-tiles` from two required direct cells to five direct
   cells.
4. `assets-src/image/manifests/phase2-visual-manifest.json` receives canonical
   entries; `client/src/main/resources/manifests/visual-manifest.json` remains
   generated by `syncPhase2Manifests`.
5. Runtime selection consumes manifest-resolved exact keys; it must not keep an
   owner-key inventory mirror in production Kotlin.

Use existing manifest `tags` to declare the family without a manifest schema
change:

```text
terrain_variant_family:tileset.ruins.ground_01
terrain_variant_index:0
terrain_variant_index:1
terrain_variant_index:2
terrain_variant_index:3
```

The runtime contract should be:

1. `VisualManifestResolver` builds a terrain variant index from exact manifest
   entries carrying `terrain_variant_family:*`.
2. `resolveTerrainVariant(baseKey, variant)` returns an exact variant entry
   when a family exists and otherwise returns the exact base key.
3. A malformed family tag fails fast during resolver initialization when it
   points to a missing base key, uses a mismatched category, or duplicates an
   index.
4. `ClientAssetLoadStrategy.sessionLoad` expands terrain base keys to all exact
   variant family keys so preloading and asset diagnostics see the same
   resources the renderer can draw.
5. `TileRenderModelBuilder` uses the existing deterministic world-coordinate
   `materialVariant(x, y, key)` as the selection input. No system time, random
   source, save field, replay field or `core` rule change is introduced.

## Resource Direction

The four floor images must be authored as one compatible material set:

1. Same palette, light direction and slab scale.
2. Different crack paths, grime clusters and broken slab islands.
3. No baked light pools, selection frames, poison, actors, props, digits,
   labels, hotkeys or manifest keys.
4. 4x and 8x tiling preview must not expose an obvious motif cadence.
5. Each 32px downscaled cell must still read as worn stone, not flat noise.

This does not require `tileset.ruins.wall_01` variants in the first slice. Wall
crown, side shadow and door/corner contact remain visually important, but a full
wall autotile contract is a larger adjacency problem and should be a separate
decision if the floor variant family does not move the map from grid-first to
room-first.

## Rejected Options

| Option | Verdict | Reason |
| --- | --- | --- |
| Another single `tileset.ruins.ground_01` reroll | rejected | AG/AH/AI proved one tile cannot carry the room-space read; stronger details repeat as a motif. |
| More renderer micro-rectangles or alpha tuning | rejected | The goal document explicitly stops this path; it hides the resource structure problem in compositor noise. |
| Production Kotlin hard-coded list of PR-08 terrain keys | rejected | It becomes a second resource authority and conflicts with `resourcePipelineLint` intent. |
| Full wall/floor autotile schema | deferred | Stronger long-term solution, but too broad for PR-08 and risks new schema/region contract drift. |
| Change `FoundationGameSession.terrainVisualKey` to emit variants | rejected for first slice | It pushes a client presentation choice into game snapshot semantics and touches replay/save-visible contracts without need. |

   deterministic coordinate selection.
5. Keep all compositor layer-order tests intact.

## Acceptance Criteria

1. Runtime crop first reads as an authored room space, not a repeated floor
   grid.
2. Player, enemies, loot, props, selection, hazards and telegraphs remain
   readable.
3. Contact sheet proves that the four floor variants tile together without a
   dominant repeated crack or slab silhouette.
4. `resourcePipelineLint` does not report a production Kotlin owner-key mirror.
5. No generated or committed resource contains baked text, digits, hotkeys or
   manifest keys.
6. No golden baseline is updated before director-rubric self-review accepts the
   evidence.

## Rollback

The rollback path is local and explicit:

1. Remove the three variant cells from `sheet-plan.yaml`.
2. Remove the three variant entries from `key-registry.yaml`.
3. Restore `pr08-owner-keys.yaml` `r02-ui-demo-ruins-tiles` direct count to two.
4. Remove the three canonical manifest entries and resync runtime manifests.
5. Runtime resolver falls back to exact `tileset.ruins.ground_01` because no
   `terrain_variant_family` exists for that base key.

No `core`, save, replay, profile, schema version, terrain type or gameplay rule
rollback is needed if the implementation stays inside this proposal.
