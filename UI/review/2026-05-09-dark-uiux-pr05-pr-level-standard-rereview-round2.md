### [P1-1] PR close sheet count still contradicts the fixed required sheet set

Evidence:

- `UI/pr/dark-uiux-pr05-map-actor-portrait-replacement.md:120-124` freezes 16 sheet ids:
  `r02-tiles-ground`, `r02-tiles-wall`, `r02-tiles-decal`, `r03-props-interactable`, `r03-props-environment`, `r03-vfx-telegraph`, `r04-actors-player`, `r04-actors-humanoid`, `r04-actors-monster`, `r04-actors-boss`, `r05-bestiary-humanoid-icons`, `r05-bestiary-creature-icons`, `r05-boss-icons`, `r06-portraits-classes`, `r06-portraits-trees`, `r06-portraits-zones`.
- The same document still says "15 张 sheet" at `UI/pr/dark-uiux-pr05-map-actor-portrait-replacement.md:53`, `:213`, `:310`, and `:311`.
- `UI/pr/README.md:64-79` also defines these 16 PR-05 sheet ids as the ownership contract.

Impact:

The close gate, PR description, manual record, and owner-scope artifact can disagree about whether one sheet is missing. A developer can accidentally omit one required sheet while still believing the document was followed, especially because the exact command contains the 16 ids but the pass criteria says 15.

Required fix:

1. Change every "15 张" reference in PR05 to "16 张".
2. Add `requiredOwnerSheetCount=16` or equivalent wording to the PR close artifact criteria.
3. Keep the 16-id list in one code block and refer back to it from Gate Budget, implementation order, and manual record fields.

Status vs previous report: partially solved. The exact list was added, but the count was not normalized.

### [P1-4] Owner inventory is still not precise enough to generate implementation without interpretation

Evidence:

- PR05 says the inventory schema is sheet-level `sheets[].targetKeys` plus `allowAlias` at `UI/pr/dark-uiux-pr05-map-actor-portrait-replacement.md:142-165`.
- PR05 pass criteria require every non-reserved cell to have `targetKey / category / ownerPr / sheetId / fallbackKey / consumer / consumerTest / aliasOf` at `UI/pr/dark-uiux-pr05-map-actor-portrait-replacement.md:189-195`.
- `UI/pr/README.md:114-131` defines the key registry contract as per-key fields, including `targetKey`, `category`, `ownerPr`, `sheetId`, `fallbackKey`, `consumer`, `consumerTest`, and `aliasOf`.
- Current sheet-plan cell input fields are also per-cell: `row`, `col`, `targetKey`, `category`, `outputName`, `subject`, `reserved`, `aliasOf`, and `note` in `scripts/dark_sprite_sheet_contract.py:29-39`.
- Several source rules still require human categorization: "canonical `prop.*` that represents ...", "humanoid enemy `actor.*` families such as ...", "non-humanoid enemy `actor.*` families such as ...", and `vfx_plate / tile_decal` at `UI/pr/dark-uiux-pr05-map-actor-portrait-replacement.md:175-180`.

Impact:

Two developers can produce different owner inventories from the same document. The schema also cannot be copied directly into `key-registry.yaml` or `sheet-plan.yaml` because it collapses multiple keys into `targetKeys` and does not freeze row/col/outputName/alias behavior per cell.

Required fix:

Define `UI/sprite-sheets/pr05-owner-key-inventory.json` as flat `entries[]`, not only sheet-level groups. Each entry should include:

- `targetKey`
- `sheetId`
- `row`
- `col`
- `category`
- `outputName`
- `fallbackKey`
- `consumer`
- `consumerTest`
- `aliasOf`
- `playerVisible`
- `ownerPr`
- `sourceManifestPath`
- `sourceDecision`

Then change the source rules to either exact key lists or exact deterministic extraction rules with an included generated summary. Any "such as" family split must be replaced by an explicit list before implementation starts.

Status vs previous report: partially solved. The inventory concept was added, but it is still not a fully executable development input.

### [P1-5] Boss `*.visual` actor-sprite keys are omitted from PR05 ownership

Evidence:

- PR05 replaces "Boss actor sprite" at `UI/pr/dark-uiux-pr05-map-actor-portrait-replacement.md:82`.
- The `r04-actors-boss` source rule includes exactly `actor.boss.*` at `UI/pr/dark-uiux-pr05-map-actor-portrait-replacement.md:181`.
- The `r05-boss-icons` source rule includes exactly `boss.*.icon` at `UI/pr/dark-uiux-pr05-map-actor-portrait-replacement.md:184`.
- Current canonical manifest contains `boss.abyssal.guardian.visual`, `boss.cultist.dungeon_lord.visual`, and `boss.orc.molten_giant.visual` with category `actor_sprite`.
- `game/src/main/resources/data/bosses/index.yaml:21-22`, `:49-50`, and `:76-77` use `boss.*.visual` and `boss.*.icon`.
- Client presentation resolves boss visual tint keys via `TileRenderModel.actorTintColorHex` at `client/src/main/kotlin/com/ktome/client/render/TileRenderModel.kt:1218-1227`.

Impact:

PR05 can close all `actor.boss.*` and `boss.*.icon` keys while leaving canonical boss visual actor-sprite entries on the old style. If these keys are intended only as tint metadata, that exception still needs to be explicit; otherwise PR05 does not actually replace all boss visuals it claims to own.

Required fix:

Choose one contract and make it mechanical:

1. Include `boss.*.visual` in `r04-actors-boss` or a dedicated PR05 boss visual sheet, with resolver tests and owner-scope coverage; or
2. Explicitly declare `boss.*.visual` as non-goal metadata, set its future owner, and add a coverage exception explaining why it is not a player-visible sprite replacement.

Status vs previous report: new issue discovered during round 2 manifest/game-data cross-check.

### [P2-2] Actor ordering is described as test-critical, but the sort contract is not defined

Evidence:

- PR05 says "actor Y-sort / ground loot marker / boss telegraph overlay" must be locked by tests at `UI/pr/dark-uiux-pr05-map-actor-portrait-replacement.md:248-255`.
- Current `TileRenderModel` only sorts actors by player-last priority at `client/src/main/kotlin/com/ktome/client/render/TileRenderModel.kt:278-281`.
- `TileLayerComposer` composes `terrainTiles -> propTiles -> overlayTiles -> actorTiles` at `client/src/main/kotlin/com/ktome/client/render/TileLayerComposer.kt:3-10`.

Impact:

If PR05 expects real Y-sort, developers must guess whether the intended sort key is `y`, `x`, entity id, player priority, or cell occupancy. If PR05 does not intend to change ordering, calling it "Y-sort" creates an unnecessary implementation obligation.

Required fix:

Either define the exact actor ordering contract and tests, or change the wording to the actual existing invariant:

- `terrain -> prop -> overlay -> actor` layer order
- player actor drawn after non-player actor when occupying the same placement priority
- ground loot marker canvas overlay remains readable when actor-occupied

Status vs previous report: new precision issue found after checking current renderer code.

### [P2-3] VFX category ownership still allows `vfx_plate / tile_decal` ambiguity

Evidence:

- PR05 uses `vfx_plate / tile_decal` for `r03-vfx-telegraph` at `UI/pr/dark-uiux-pr05-map-actor-portrait-replacement.md:177`.

- `tile_decal`: terrain interaction decals only, if any remain in this sheet.
- `vfx_plate`: boss warning, telegraph, zone effect, and boss variant overlays.

If any existing manifest key intentionally keeps `tile_decal`, list it explicitly with category justification and consumer test.

Status vs previous report: new precision issue.

## 玩法与体验审查

PR05 is the largest visible art replacement PR in this UI sequence. The current doc now frames the right player-facing outcomes: dark map tiles, actors, boss telegraphs, bestiary icons, portraits, and zone visuals. The remaining UX risk is not broad direction; it is exactness.

The key player-visible risks are:

1. Boss visuals can remain inconsistent if `boss.*.visual` is not either replaced or explicitly deferred with a visible/non-visible decision.
2. Actor readability can regress if "Y-sort" is implemented differently by different developers.
3. Telegraph readability can regress if `tile_decal` and `vfx_plate` categories are mixed without exact category rules.
4. Screenshot evidence can become non-reproducible if the scenario id and seed are invented during implementation.
