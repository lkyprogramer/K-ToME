## 0. 总体评价

Phase 3 文档体系的整体质量高于大多数独立游戏项目的设计阶段文档。**六大工作包的划分思路正确**，出口门禁与验证清单也体现了工程纪律。但在细读之后，发现若干设计层面的空洞和工程层面的隐患，如不在编码开始前修复，**很可能在 P3-C 阶段收尾时引发大规模返工**。

评审按"最大胆的重构建议 → 中等优先级的系统性问题 → 细节优化"三层展开。

## 1. 最大胆的重构建议（改变整体结构）

### 1.1 🔴【P0-ARCH-01】工作包必须从"顺序链"重构为"平行四线"

**问题所在**

当前六个工作包的实际依赖关系是：

```
W1 → W2 → W3 → W5
             ↘ W4 ↗ W6
```

几乎是一条顺序链：W1 完成前 W2 无法开始，W2 完成前 W3 无法开始……这与路线图第 5.1 节明确提出的"四条并行开发线（Rules Lane / Client Lane / Content Lane / Tools/QA Lane）"原则**完全矛盾**。

**后果**

- 任何一个包的延误会直接阻塞全链，总工期等于所有包的串行总和，没有缓冲。
- 四条开发线的优势（AI 工程师、内容设计师、前端工程师可以并行）被完全浪费。

**重构建议**

将工作包按"系统骨架"与"内容填充"解耦，**允许 Content Lane 和 Client Lane 提前启动**：

| ID | Lane | 前置 | 内容 |
|---|---|---|---|
| P3-W1 | Rules | Phase 2 | 战斗公式 V2 + CombatTrace |
| P3-W2a | Rules | P3-W1 | 状态生命周期骨架（数据结构 + 堆叠规则）|
| P3-W2b | Client | P3-W1 | 状态 UI 语义层（与 W2a 并行）|
| P3-W3 | Rules | P3-W1, P3-W2a | TalentTree V2 + 动态说明 |
| P3-W4a | Rules | P3-W2a | AIProfile DSL 核心语法 + BossEncounter |
| P3-W4b | Client | P3-W4a | telegraph renderer（与 W4a 并行）|
| P3-W5 | Content | P3-W3 | 职业正式树 + 种族 |
| P3-W6a | Content | P3-W3 | 世界分支 YAML + zone 入口数据 |
| P3-W6b | Rules | P3-W4a, P3-W5 | affix v1 + 经济循环规则 |
| P3-W6c | Tools | P3-W6a, P3-W6b | 长局回归实验室 |

这样 W2b、W4b 可以并行推进，W6a 可以在 W3 完成后立即启动，**总 critical path 可压缩 20~30%**。

### 1.2 🔴【P0-ARCH-02】AIProfile DSL 在本阶段是最大的"无规格空洞"，必须先立规格再动手

**问题所在**

整个 P3-W4 的核心交付是"AIProfile DSL"，但全文没有一行 DSL 语法示例。战斗公式有详细的公式和 Kotlin 骨架，状态系统有 enum 定义，天赋有完整的 YAML schema——**唯独 AI DSL 是一个空的文字描述**。

实践中，AI DSL 一旦开始写，就会出现"每个 Boss 设计师自己发明语法"的问题，导致：
- Boss 之间行为不一致
- telegraph renderer 无法通用
- 后续 P5-W1（战术 AI 升级）需要大规模重写

**重构建议**

在 P3-W4 开始实现之前，**单独输出一份 AIProfile DSL Spec**（哪怕 2 页），至少覆盖：

```yaml
# 最小 DSL 规格骨架示例（评审者建议，非最终设计）
ai_profile:
  id: "iron_golem_standard"
  perception_range: 8
  last_known_position: true   # 只基于最后已知信息行动

  phases:
    - id: "phase_full"
      condition: "hp_percent > 0.50"
      actions:
        - type: MOVE_TOWARD_PLAYER
          weight: 30
        - type: USE_ABILITY
          ability_id: "stomp"
          condition: "target_adjacent"
          weight: 70

    - id: "phase_enraged"
      condition: "hp_percent <= 0.50"
      on_enter_telegraph:
        shape: CIRCLE
        radius: 4
        duration_turns: 1
        danger_level: HIGH
      actions:
        - type: USE_ABILITY
          ability_id: "ground_slam"
          weight: 80

  boss_phases:
    - threshold_hp_percent: 0.50
      transition: "phase_enraged"
      invulnerable_turns: 1
```

没有这个规格，P3-W4 的"完成定义"无法被客观验证。

### 1.3 🟠【P1-ARCH-03】Roguelike 最核心的"局间循环"在 Phase 3 是空白

**问题所在**

Phase 3 负责建立"4~6 小时长局"，但文档完全聚焦在局内系统（战斗、状态、职业、世界），对以下问题保持沉默：

1. 玩家在第 3 小时死亡后，**是否从头开始？**
2. 跑通一局后，下一局的**差异化驱动力**是什么？（这是 Phase 4 的课题，但 Phase 3 至少需要定义"本阶段的最小局间结构"）
3. **种族/职业组合的解锁路径**是什么？进阶职业的解锁条件（"Vanguard 通关任意难度"）——通关的定义是什么？

**建议**

在 Phase 3 文档中补充"最小局间合同"章节，明确：
- 本阶段是纯 Roguelike（每次死亡重置，无 meta-progress）还是有"尸体/遗物继承"机制
- "通关"的技术定义（击败最终 Boss `深渊之心`？还是到达某个节点？）
- 进阶职业解锁的持久化机制（存在哪里？如何不被存档失效清零？）

## 2. 系统性设计问题（P1 级别，必须在 W 包开始前对齐）

### 2.1 🔴【P0-SYS-01】状态列表范围模糊：P2 已有的状态和 P3 新增的状态边界不清

**问题所在**

Phase 3 主文档第 4.2 节列出的"本阶段必须正式化的状态"为：
> `STUN / ROOT / SILENCE / BLEED / BURN / CURSED / GUARD / STEALTH / BANE`

但核心系统设计文档（第 4.6 节）明确标注 `ROOT、SILENCE、BLEED、BURN、GUARD` 均在 **Phase 2** 引入。这带来两个问题：

1. Phase 3 文档是在说"Phase 2 引入但未正式化的状态"还是"Phase 3 新增的状态"？界定不清。
2. 核心系统文档中标注为 P3 引入的 `INVULNERABLE`（无敌）和 `TAUNT`（嘲讽）完全未出现在 Phase 3 主文档中，**但这两个状态对 Boss 设计非常关键**（不死鸟天赋依赖 `INVULNERABLE`，战卫嘲讽天赋依赖 `TAUNT`）。

**修复建议**

Phase 3 主文档应改为：
- 明确说明"以下状态从 P2 临时状态升级为 P3 正式主线，生命周期必须可追踪"（已在 P2 骨架中存在的）
- 明确说明"以下状态为 P3 新增"（`OVERCHARGE、BANE、CURSE、WEAKEN、INVULNERABLE、STEALTH、TAUNT`）
- `CURSED` 应统一为 `CURSE`（与核心系统文档保持一致，避免拼写漂移）

---

### 2.2 🟠【P1-SYS-02】HASTE/SLOW 互消规则缺少量级定义

**问题所在**

Phase 3 主文档第 4.2 节规定：
> `HASTE 与 SLOW 互相抵消`

但没有定义量级处理逻辑：
- 1 层 SLOW 被 1 层 HASTE 抵消？还是看"速度修正值"的绝对量？
- 如果玩家有 `HASTE x2`（+40% 速度）同时中了 `SLOW x1`（-30% 速度），结果是 +10% 速度？还是两者都清除只剩 1 层 HASTE？
- 互消后的事件触发顺序（是否触发状态清除回调？）

这个规则在 Boss 战中会被频繁测试，不明确就会出现实现分歧。

**修复建议**

明确采用**净值计算**模型：`effectiveSpeed = base + sum(allHasteModifiers) + sum(allSlowModifiers)`，HASTE 和 SLOW 都作为 `speedModifier` 叠加，不需要"互消"概念；或者采用"最后施加者覆盖"模型。**选一个，写进 status 生命周期规格中**。

---

### 2.3 🟠【P1-SYS-03】SHIELD 和 REGEN 的"取较强值"语义不完整

**问题所在**

Phase 3 主文档规定 `SHIELD` 和 `REGEN` 采用"取较强值"叠加模式，但：
- "较强值"的判断维度是什么？仅比较"吸收量"？还是同时比较"持续时间"？
- 一个护盾吸收 50 伤害剩余 3 回合，另一个可以吸收 30 伤害剩余 8 回合，哪个"更强"？
- 如果新施加的护盾比当前护盾弱，是完全丢弃新护盾，还是取持续时间较长者？

**修复建议**

明确协议为：**同一来源刷新（同 id 的 SHIELD 刷新吸收量和持续时间），不同来源共存**。或者定义一个简单的比较规则，例如"按剩余吸收量从大到小最多保留 2 个护盾"。

---

### 2.4 🟠【P1-SYS-04】Boss Phase 切换的技术规格缺失

**问题所在**

Phase 3 主文档提到 `BossPhaseDef`，但没有任何技术规格。Boss phase 设计涉及：
- 切换条件（HP 百分比？时间？触发特定状态？）
- 切换时机（在受到致命一击时立即切换？还是在回合开始时判断？）
- 切换期间的无敌帧（是否有 `invulnerableTurns`？）
- Phase 切换是否重置 AI 行为树的状态机？
- Phase 切换时已施加在 Boss 身上的状态如何处理（是否清除）？

这些都在 ARCH-02 里提到的 DSL 规格中应该覆盖，但当前是纯空洞。

---

### 2.5 🟠【P1-SYS-05】进阶职业 schema 冻结与实际内容量之间的预算矛盾

**问题所在**

Phase 3 主文档要求"4 个进阶职业的 schema、资源、定位与 profile 必须在本阶段冻结"，同时要求"2 个进阶职业必须在本阶段进入可玩路径"。

但核心系统设计文档对 Shadowblade 和 Warden 的描述只有半行（"暗杀术、暗影步法、毒术、夜行者"），而 Berserker/Spellblade 也只有天赋树方向名称，没有任何具体天赋设计。

这就意味着"冻结 schema"本身需要一个不小的设计工作量——但这个工作量没有被单独识别为工作包或子任务，**很容易在 P3-W5 开始时才发现设计不够用**。

**修复建议**

- 要求在 P3-W5 开始前，先输出 Shadowblade 和 Warden 的"最小设计文档"（每职业 1 页，包含资源轴、3 棵天赋树的方向、signature ability、panic answer）。
- 将这个设计输出作为 P3-W4 和 P3-W5 之间的**前置交付物**。

### 2.6 🟠【P1-SYS-06】种族数量：3 个还是 5 个？文档自相矛盾

**问题所在**

Phase 3 主文档第 4.4 节规定：
> `3 个种族和本地 Profile 进入主线验证`

但核心系统设计文档第 5.3 节定义了 5 个种族：人类、精灵、矮人、兽人、亡者。

"3 个种族"是哪 3 个？这会影响：
- Content Lane 的种族天赋 YAML 工作量（3 × N 天赋 vs 5 × N 天赋）
- 白盒验证的覆盖范围
- 进阶职业解锁条件中是否包含种族约束

**修复建议**

明确指定 Phase 3 进入主线的 3 个种族（建议：人类、精灵、矮人，覆盖近战/速度/韧性三个方向），并声明"兽人、亡者进入 Phase 4 schema 冻结但内容后补"。

### 2.7 🟠【P1-SYS-07】铭文系统"最小合同"不够最小——缺少内容设计

**问题所在**

Phase 3 主文档定义铭文最小合同为：最多 4 个、同类最多 2 个、热键 5~8、只受冷却控制。这是**操作约束**，但没有任何**内容设计**：铭文做什么？

铭文系统是 ToME 原版的核心构筑差异化来源。如果只有骨架没有内容，那这个"build 轴"就是空的，职业构筑的多样性也无法体现。

**修复建议**

- 在 P3-W2（状态/铭文骨架）中，**必须同时交付至少 8~10 个铭文的初始内容**（即使是简单的）：如"火焰铭文：主动触发 BURN 3 回合，CD 4"、"护盾铭文：获得吸收 20 点的 SHIELD，CD 6"等。
- 否则铭文系统的"可验证性"无从建立。

### 2.8 🟠【P1-SYS-08】长局结构"经济循环"缺乏具体设计

**问题所在**

Phase 3 主文档第 4.6 节提到"掉落与构筑要形成正反馈，经济循环"，但没有定义：
- 货币是否存在？（金币？特殊货币？）
- 商店是否存在于长局中？在哪些 zone？
- 物品可以在局内怎么处理（卖/合成/强化）？
- "掉落驱动构筑差异"的具体机制是什么？是靠 affix 词条组合，还是有特殊的成型机制？

没有这些定义，`affix v1` 的设计就没有着力点，"经济循环"实际上是空话。

**建议**

补充一个"最小经济模型"章节，哪怕只有：
1. 是否有局内商店（建议：有，1~2 个固定商店节点在 zone 之间）
2. 交换媒介（建议：使用"碎片"作为唯一货币，怪物掉落，商店购买装备）
3. 局内强化是否存在（建议：Phase 3 只做基础购买，Phase 4 再做打造/附魔）

## 3. 技术规格问题（P1 级别）

### 3.1 🟠【P1-TECH-01】CombatPipeline 12 步骤与 Phase 3 文档规格存在写法差异

**问题所在**

Phase 3 主文档 4.1 节中的命中公式写法：
```
hitChance = clamp(0.05 + 0.90 * sigmoid(0.04 * (accuracy - evasion + 10)), 0.05, 0.95)
```

核心系统设计文档 3.2.1 节写法（参数等价但形式不同）：
```
d = accuracy - evasion
m = -10
sigmoid(d) = 1 / (1 + e^(-k * (d - m)))
hitChance = 0.05 + 0.90 * sigmoid(d)
```

两者数学等价（`d - m = d + 10`），但**形式不同会导致实现歧义**——尤其是 AI 辅助编码时，两个不同文件给出不同形式，AI 可能实现出两个版本都"看起来对"但互不一致。

**修复建议**

Phase 3 主文档应显式标注"公式与核心系统设计文档 3.2.1 节保持一致，以该节为权威，此处为便于阅读的等价形式"。或者直接统一为同一形式。

---

### 3.2 🟠【P1-TECH-02】CombatTrace 金样本重录是破坏性变更，需要显式版本化协议

**问题所在**

Phase 3 主文档 4.1 节明确指出：
> `Phase 3 切换到正式公式后，Phase 2 的 CombatTrace / Golden Seed 基线必须全量重录，这是预期内破坏性变更。`

这个声明是正确的，但**没有定义重录的版本化协议**：
- 重录后的 golden 文件放在哪里？是覆盖原 Phase 2 golden 还是新建 Phase 3 golden？
- 如何防止"忘记重录导致 CI 用旧 golden 通过"的情况？
- 是否有一个 `phase` 字段在 golden 文件中标记其有效阶段？

**修复建议**

在验证清单中增加"所有 Phase 3 golden 文件必须包含 `phase: P3` 标记，CI 门禁必须校验 golden 与当前阶段标记一致"。

---

### 3.3 🟡【P2-TECH-03】respec/rollback 的成本约束未定义

**问题所在**

Phase 3 主文档要求 respec 和 rollback 必须有自动化回归，但没有定义：
- Respec 是否有成本（金币？回城才能洗？还是随时免费）？
- Rollback 的粒度是什么（单个天赋？整棵树？）
- 洗点后是否有"CD"或"每局限次"？

这些是玩法层面的决策，会直接影响构筑体验。更重要的是：**自动化测试的验证目标会因此不同**。

**建议**

Phase 3 明确一个最简洗点方案并冻结：建议"局内免费洗点，但只能在非战斗状态，洗点清空所有天赋点并退还"。哪怕这个方案将来变化，至少当前测试有明确目标。

---

### 3.4 🟡【P2-TECH-04】断点成长的 UX 表现未定义

**问题所在**

天赋的断点成长（breakpoint）在 schema 中有定义，但没有说明玩家看到什么：
- 升级到断点时，UI 如何通知玩家出现了新效果？
- 动态说明如何区分"当前等级效果"和"下一断点效果预览"？
- 断点未达到时，描述文本是否显示"灰色预览"？

这是 Client Lane 的设计依赖，如果不在 P3-W3 前确定，Client 实现会走错方向。

---

### 3.5 🟡【P2-TECH-05】长局实验室（longRunLab）的验收标准不够精确

**问题所在**

验证清单中 longRunLab 的要求：
> `4~6 小时 run 可结束、无卡死、无不可达主线`

但缺少：
- **时间度量方式**：headless run 不是真实 4 小时，如何换算"等价回合数"？
- **死亡可接受性**：玩家死亡算"结束"吗？还是只有通关才算"结束"？
- **种族/职业覆盖范围**：实验室跑哪些组合？全部？还是至少覆盖代表性构筑？

**建议**

将长局实验室拆为：
- `longRunLab --smoke`：固定种族 + 职业 + seed，验证"可到达终局状态"（不要求通关）
- `longRunLab --full`：全职业矩阵，统计死亡分布和平均时长

## 4. 细节优化建议（P2 级别）

### 4.1 🟡 ARMOR_BREAK 与不同来源的叠层逻辑

主文档规定 `ARMOR_BREAK` 最多 3 层，但没有说明"来源不同的 ARMOR_BREAK 是否独立计算层数"——战卫有天赋可以破甲，游荡者也有，如果两者同时对同一目标叠加 ARMOR_BREAK，3 层是全局上限还是每来源上限？建议：全局上限，与来源无关。

### 4.2 🟡 STEALTH 被 AoE 打破的范围定义

主文档规定"STEALTH 被任意 AoE 伤害打破"，但 AoE 的范围判定需要明确：目标处于 AoE 范围内但未受到伤害（因为命中失败）是否打破 STEALTH？建议：以"实际受伤"为触发条件，而非"目标在 AoE 范围内"。

### 4.3 🟡 世界分支的主线 zone 名称与终线 zone 名称不一致

主文档 4.6 节第一处列出：`shattered_outpost -> greenwood_fringe -> deep_iron_pit -> grey_gate_depths`

第二处列出：`地下河 -> 水晶洞穴 -> 深渊神殿 -> 深渊之心`

两条路径是并列的可选路线，还是主线 + 扩展终线的层级关系？如果是后者，应该明确连接节点（即哪个 zone 可以进入地下河？`grey_gate_depths` 之后？）。建议在 zone 结构图中用显式的图示而非两段文字分开描述。

### 4.4 🟡 Spellblade 的 EQUILIBRIUM 资源机制需要更多边界定义

核心系统文档定义 EQUILIBRIUM "起始 50，根据最近使用的技能流派每回合偏移 3 点"，但没有定义：
- "最近使用的技能流派"如何判定：看上一个动作？还是过去 N 个动作的加权？
- 偏移到两端（0 或 100）时是否有视觉/音效反馈？
- 同一回合使用了一个物理技能和一个法术技能，EQUILIBRIUM 如何变化？

这是 Spellblade 的灵魂机制，模糊会导致整个职业手感不对。

### 4.5 🟡 affix v1 预算与 4~6 小时游戏时长的匹配性存疑

Phase 3 定义 affix v1 总量：武器前缀 12、后缀 10、防具前缀 10、后缀 8，共 40 条。

对于一个 4~6 小时的 roguelike run，玩家会装备 6~8 件物品，每件 1~2 个 affix，一局约接触 10~16 个不同词条。40 条总量理论上覆盖 2~3 局，但如果词条分布不均（常见/稀有权重差异大），**玩家实际感受的词条多样性可能只有 12~15 条**。这对于 Phase 3 可以接受，但应该明确"Phase 3 的 affix 系统目的是验证掉落驱动构筑差异，而非提供完整的构筑多样性——后者由 Phase 4 完成"。

### 4.6 🟡 净化优先级"可配置"但未给出第一版配置

主文档规定"净化优先级必须可配置，并明确不可被净化的效果集合"，但没有给出第一版配置。

建议明确：
- 不可净化效果：`INVULNERABLE`、`KNOCKBACK`（瞬时，无意义净化）、Boss 专属状态
- 默认净化策略：优先清除持续时间最长的负面状态；如果有 `STUN`/`ROOT` 则优先清除

### 4.7 🟡 验证清单缺少"新旧公式切换的差异量化"

当 Phase 3 公式切换后，理论上同等角色在同等情景下的伤害数值会有所变化。验证清单应包含：
> "在固定测试场景（标准角色 vs 标准怪物）下，P3 公式的伤害输出与 P2 公式相比在合理范围内（建议：±30%），不出现数量级差异"

这可以防止公式参数设置错误导致全局伤害数值崩塌。

## 7. 评审结论

**Phase 3 是这个项目最关键的阶段**——它决定这个游戏是否真正"好玩"，而不仅仅是"可运行"。战斗公式、职业构筑、Boss 电报，这些系统组合在一起才能产生"Roguelike 深度感"。

当前文档体系的工程纪律和验收标准是可信赖的。**主要风险不在"做什么"，而在"怎么并行做"和"某些系统内部规格是否足以支撑实现"**。

最核心的两个建议再次强调：

1. **先立 AIProfile DSL 规格，再动手写 W4**——没有规格的 DSL 是一场灾难。
2. **把工作包从顺序链改为并行线**——这是 Phase 3 能否在合理时间内完成的关键。

其余 P1/P2 问题均可在对应工作包开始前的"设计 spike"中解决，不构成阶段启动阻塞。
