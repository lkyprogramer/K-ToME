# Phase 1 - 1-1.0 Foundation & Verifiable Core

**阶段**: `1-1.0`  
**优先级**: `P0`  
**对应问题**: 当前仓库只有文档与工具链基线，没有真正的多模块工程、核心内核或可运行切片；如果这一阶段不同时建立测试与覆盖率门禁，后续所有阶段都会失去可自证能力。

---

## 1. 阶段目标

把当前仓库从“只有规划文档”推进到“具备可验证内核与最小可运行 client 壳层”的状态。

完成标准：

1. 项目具备 `root / core / game / client` 多模块结构。
2. `core` 中完成 ECS、地图、BSP、FOV 等纯逻辑基础设施。
3. `client` 可以在 libGDX 窗口中渲染 ASCII 地牢与玩家 `@`。
4. `@` 可以在 BSP 地牢中 8 方向移动，FOV 实时更新。
5. `./gradlew test`、`jacocoTestReport` 与 `:core:jacocoTestCoverageVerification` 全部可执行。

---

## 2. 当前问题

1. 当前没有实际的模块目录与源码结构。
2. 当前没有任何测试、coverage、CI 级别的失败门禁。
3. 当前没有最小 client 运行壳层，因此无法验证 `core` 与 `client` 的边界是否干净。
4. 如果不先把地图、FOV 和移动链路打通，后续战斗/AI/物品的调试都会缺少真实场景。

### 2.1 基于当前仓库的输入事实

1. Java / Kotlin / Gradle 项目级版本已经固定：
   - Java `21`
   - Kotlin `2.2.21`
   - Gradle Wrapper `8.14.3`
2. 根目录已存在最小 `build.gradle.kts` 与 `settings.gradle.kts`，但仅用于生成 Wrapper。
3. `docs/mvp-development-guide.md` 已给出目标模块结构与核心类型列表。

## 3. 范围与非目标

### 3.1 范围

1. 多模块工程骨架
2. `core` 的 ECS / map / BSP / FOV
3. `game` 的最小数据入口占位
4. `client` 的 ASCII 渲染、摄像机、输入与移动接线
5. JaCoCo 与覆盖率门禁

### 3.2 非目标

1. 不在本阶段实现怪物 AI、战斗、物品、天赋、存档。
2. 不在本阶段引入 Lua、mod runtime 或复杂资源管线。
3. 不在本阶段引入 tile 渲染或正式美术资源。
4. 不在本阶段追求高性能 ECS。

---

## 4. 技术方案

### 4.1 工程结构冻结

必须落成如下结构：

```text
K-ToME/
├── build.gradle.kts
├── settings.gradle.kts
├── gradle.properties
├── core/
├── game/
└── client/
```

推荐包路径：

```text
core/src/main/kotlin/com/ktome/core/
game/src/main/kotlin/com/ktome/game/
client/src/main/kotlin/com/ktome/client/
```

### 4.2 构建与门禁冻结

1. 根构建中统一声明：
   - Kotlin JVM
   - JaCoCo
   - JUnit 5
   - Kotest assertions
2. `core` 必须通过依赖检查证明不含 libGDX。
3. `1-1.0` 必须补齐：
   - `jacocoTestReport`
   - `jacocoTestCoverageVerification`
4. 建议把 `check` 依赖到 `jacocoTestCoverageVerification`，避免只生成报告不失败。

### 4.3 ECS 冻结口径

首版不做 archetype、sparse set、system scheduler 优化，直接采用最简可测实现：

1. `EntityId`
2. `World`
3. 组件存储
4. `entitiesWith(vararg types)`
5. `GameSystem`
6. `World.update()` 按 `priority` 排序执行

`1-1.0` 的目标是“稳定 + 清晰 + 可测”，不是“高性能”。

### 4.4 地图与 BSP 冻结口径

1. `GameMap` 必须是纯数据结构。
2. `BSPGenerator` 必须支持固定 seed，确保测试可重复。
3. 地图必须至少具备：
   - 房间
   - 走廊
   - 墙 / 地板
   - 起点
4. 生成器输出必须能直接被 FOV 与移动系统消费。

### 4.5 FOV 冻结口径

1. FOV 算法采用 shadowcasting。
2. FOV 计算函数必须是纯函数：
   - 输入地图、原点、半径
   - 输出可见格集合
3. 不允许把渲染状态混入 FOV 逻辑。

### 4.6 Client 最小壳层冻结

1. `client` 只需完成：
   - 窗口创建
   - ASCII 网格渲染
   - 键盘输入
   - 摄像机 / viewport
2. 玩家 `@` 的移动必须直接消费 `core` 的地图/FOV 结果。
3. 不在 `client` 实现地图生成逻辑，不在 `client` 存储权威地图状态。

### 4.7 自证链路必须在本阶段建立

本阶段不是“先写完功能再补测试”，而是必须同步补齐：

1. `WorldTest`
2. `BSPGeneratorTest`
3. `ShadowcastingTest`
4. client 手动白盒验证步骤
5. JaCoCo 覆盖率门禁

## 6. 测试与自证

### 6.1 必测类

1. `core/src/test/kotlin/com/ktome/core/ecs/WorldTest.kt`
2. `core/src/test/kotlin/com/ktome/core/map/BSPGeneratorTest.kt`
3. `core/src/test/kotlin/com/ktome/core/fov/ShadowcastingTest.kt`

建议补充：

1. `GameMapTest.kt`
2. `MovementRulesTest.kt`

### 6.2 必须覆盖的行为

1. 实体创建/销毁与组件生命周期
2. `entitiesWith` 查询正确性
3. System 执行顺序
4. BSP 房间不重叠、连通性与边界合法性
5. FOV 被墙遮挡的阴影行为
6. 玩家不能走进墙、不能越界
7. 同一 seed 的地图生成结果稳定

### 6.3 覆盖率门禁

1. `ecs / map / fov` 包行覆盖率 `>= 85%`
2. `core` 总体行覆盖率 `>= 60%`

### 6.4 自动化命令

```bash
./gradlew test
./gradlew :core:test
./gradlew jacocoTestReport
./gradlew :core:jacocoTestCoverageVerification
./gradlew :client:run
```

### 6.5 白盒验证

固定白盒验证步骤：

1. 启动 `./gradlew :client:run`
2. 进入地图后观察 `80x50` 网格是否正确渲染
3. 使用 8 方向按键移动玩家
4. 确认：
   - 墙体阻挡有效
   - FOV 随移动刷新
   - 摄像机不抖动
   - 未可见区域不泄露信息

---

## 8. 风险与止损

1. 风险：过早追求高性能 ECS。  
   止损：明确只做最简可测实现，性能优化全部后置。
2. 风险：把地图/FOV 状态做进 `client`。  
   止损：`client` 仅消费 `core` 输出，不持有权威规则。
3. 风险：只生成 JaCoCo 报告，不做失败门禁。  
   止损：本阶段必须接入 `jacocoTestCoverageVerification`。
4. 风险：地图生成依赖随机数而不可复现。  
   止损：所有生成器测试都使用固定 seed。
