# 一、项目背景

这是一个 **类 ToME（Tales of Maj'Eyal）方向的单机 Roguelike / RPG 游戏项目**。  
项目目前已经完成 **phase4** 的全部开发工作。  
phase4 的设计文档和优化改进文档位于：

- `docs/phase4/` 
- `docs/review/phase4/opt/PR` 

你需要同时站在以下几个视角进行审阅：

1. **设计一致性视角**  
   检查当前实现与`docs/phase4/`,`docs/review/phase4/opt/PR` 是否存在：
   - 文档已设计但未实现
   - 已实现但与设计偏离
   - 实现细节破坏了原始设计目标
   - 多个系统之间互相冲突
   - 文档写得通，但落地后实际体验不成立

2. **可玩性 / 耐玩性 / 好玩视角**  
   不只是看“功能有没有做完”，而是看在 **Phase4 当前这个完成态** 下，游戏是否已经具备：
   - 能让玩家持续玩下去的核心动力
   - 足够清晰的短中期目标
   - 让玩家愿意继续探索、构筑、战斗、刷资源、尝试新打法的驱动
   - 不依赖未来 phase 才成立的体验闭环

3. **当前阶段必须优化视角**  
   你的任务不是把问题推给  Phase5。  
   只要某个问题在 **当前 Phase4 就应该优化**，就必须明确指出，并给出优化建议。  
   除非该问题确实受到阶段边界限制，否则 **不允许用“后续阶段再做”来回避当前问题**。

# 二、审阅目标

请完成以下 4 个核心任务：

## 任务 A：Phase4设计实现一致性审查
对照 `docs/phase4/`,`docs/review/phase4/opt/PR` 的所有设计文档逐项核查当前项目实现情况，至少回答：

- Phase4 承诺的功能是否全部存在？
- 每个功能是否按文档预期工作？
- 具体实现是否偏离设计意图？
- 是否存在“功能上完成了，但体验上不成立”的伪完成项？
- 是否存在文档没要求但实现里额外加入、且可能破坏体验的内容？

请输出一个 **功能/系统一致性矩阵**，至少包含：

- 模块/系统名
- 文档设计摘要
- 当前实现状态（已实现 / 部分实现 / 未实现 / 偏离实现）
- 证据锚点（文档路径、代码路径、资源路径、配置路径）
- 偏差说明
- 严重级别（Critical / High / Medium / Low）

---

## 任务 B：从“现在就要好玩”的角度做深度玩法审查
不要只看有没有系统，要看这些系统在当前 phase4 下是否已经构成了一个成立的游戏体验闭环。  
重点审查以下维度：

### 1. 核心循环（Core Loop）
检查当前游戏是否已经形成可成立的核心循环，例如：

- 进入地图 / 探索
- 遭遇战斗
- 获取奖励
- 角色成长 / 装备提升 /技能强化 /资源积累
- 解锁新的选择
- 驱动继续下一局 / 下一层 / 下一次尝试

你要判断：
- 这个循环是否顺畅
- 哪个环节最弱
- 是否存在“有流程但没有爽点”的问题
- 是否存在“前10分钟能玩，30分钟后失去动力”的问题

### 2. 战斗体验
重点看：
- 战斗决策是否足够有意义
- 不同职业 / 流派 / 技能是否真的产生差异
- 战斗节奏是否拖沓、单调、爆发失衡或反馈不足
- 玩家是否能从战斗中持续获得“判断—执行—反馈”的正循环
- 是否存在最优解过强，导致构筑空间被压扁

### 3. 角色成长与构筑驱动
重点看：
- 升级、技能、属性、装备、资源系统是否形成真实成长感
- 成长是否只是数值上涨，还是能改变玩法
- 当前阶段是否已经有足够的构筑分化
- 玩家是否会产生“这局我想试另一种 build”的动力
- 是否存在成长感弱、构筑分歧不明显、决策假选择的问题

### 4. 奖励驱动与掉落体验
重点看：
- 奖励是否足够频繁且有层次
- 奖励是否真的影响下一步决策
- 掉落 / 商店 / 宝箱 / 任务 / 里程碑奖励是否有记忆点
- 奖励曲线是否太平、太抠、太随机或太失控
- 玩家是否能感受到“每次战斗、探索、冒险都有价值”

### 5. 探索与新鲜感
重点看：
- 地图、事件、敌人、奖励组合是否足以支撑初步重复游玩
- 是否存在内容重复度过高的问题
- 探索过程是否有未知感、风险感、发现感
- 当前阶段是否已经有足够的“再来一局”的理由

### 6. 新手体验与信息反馈
重点看：
- 玩家是否容易理解当前目标
- UI / 日志 / 提示 / 数值反馈是否清晰
- 死亡、失败、受伤、资源损失是否“可理解”
- 玩家是否知道自己为什么输、为什么强、为什么下一步值得继续

### 7. 系统耦合与体验断层
重点看：
- 各系统之间是否互相支持，还是各做各的
- 是否存在“战斗是战斗、装备是装备、奖励是奖励，但彼此没形成联动”的问题
- 是否存在体验断层：菜单层、战斗层、探索层、成长层切换不顺

## 任务 C：识别“当前 Phase4 必须解决”的问题
请特别识别以下问题：

1. **当前阶段不修，后续只会越积越重的设计债**
2. **会直接损害游戏好玩程度的结构性问题**
3. **会导致后续 content expansion 建在错误地基上的系统问题**
4. **看起来小，但会严重影响玩家留存、节奏、理解成本的体验问题**

请对每个问题明确判断：

- 为什么这是 **Phase4 就必须处理** 的问题
- 为什么不能简单推迟到后续 Phase
- 如果不修，会对后续开发或玩家体验造成什么连锁影响

## 任务 D：给出可执行的优化方案，而不是空泛建议
每个重要问题都必须给出 **可在当前阶段落地的优化建议**，建议要尽量具体，避免泛泛而谈。

- 影响范围

- 具体改法

- 预期收益
- 可能副作用 / 风险
- 是否需要同步修改文档、配置、数值、UI、资源、代码架构

# 三、审阅要求（硬约束）

## 1. 必须基于证据
所有结论都尽量附带证据锚点，例如：

- 文档路径
- 代码文件路径
- 关键类 / 方法 / 配置项 / 资源文件
- UI 表现位置
- 数据结构 / 数值配置
- 日志与状态流转

禁止无依据地空谈。

---

## 2. 不要只做“代码 review”
这不是单纯代码规范检查。  
你必须从 **游戏设计、玩家体验、系统联动、数值成长、反馈质量、耐玩性** 的角度审阅。  
代码是否优雅不是本次重点，重点是：**这套东西玩起来成立不成立。**

---

## 3. 不允许把当前问题偷渡到未来阶段
除非有明确的阶段边界阻碍，否则默认：
- 能在 Phase4 优化的，就应该在 Phase4 优化
- 影响核心体验的，就必须指出现在修
- 后续阶段只能做扩展，不能用来掩盖当前体验缺陷

如果你判断某项只能放到未来阶段处理，必须说明：
- 为什么当前阶段不能做
- 缺失的前置条件是什么
- 当前能否做一个过渡性优化版本

---

## 4. 不要输出“正确但没用”的建议
例如这类空话要避免：

- 增加内容丰富度
- 优化战斗体验
- 增强成长感
- 提高奖励吸引力

你必须说清楚：
- 哪一块具体有问题
- 具体差在哪里
- 应该怎么改
- 改完会让哪个体验环节变好

---

## 5. 优先找结构性问题
优先级从高到低如下：

1. 核心循环不成立
2. 关键系统设计偏差
3. 奖励 / 成长 / 战斗驱动不足
4. 构筑深度不足
5. 信息反馈不清
6. 数值节奏问题
7. 内容量不足但结构正确的问题

---

6. 识别当前必须修复的问题与可延后问题
7. 最后给出按优先级排序的改进清单

明确回答：
- 当前 Phase4 是否达到了文档预期
- 当前版本是否已经“好玩”
- 当前版本是否具备“耐玩雏形”
- 是否适合进入下一阶段开发
- 进入下一阶段前必须先补的内容有哪些

# 六、输出质量要求

请确保报告具备以下特征：

- 结论明确，不模糊
- 批评直接，不粉饰
- 建议具体，可执行
- 以当前阶段为中心，不逃避问题
- 重点讨论“游戏体验是否成立”，而不是只讨论“功能做了没有”

如果发现当前项目存在“功能完成度看起来不错，但实际并不好玩”的情况，请直接指出，并拆解原因。
如果发现某些设计文档本身就存在问题，也请明确指出，不要默认文档一定正确。

额外要求：

- 不要默认“能运行”就等于“设计成立”
- 不要默认“和文档一致”就等于“游戏体验正确”
- 请主动寻找：
  - 伪完成功能
  - 低价值系统
  - 没有形成正反馈的奖励设计
  - 构筑表面很多但实质单一的问题
  - 会在后续 content 扩张时放大的坏地基
- 对每个系统都问一遍：
  - 它是否真的提升了玩家体验？
  - 它是否只是增加复杂度而没有增加乐趣？
  - 它是否在当前阶段就已经值得存在？
- 如果某项设计让游戏变得更复杂但没有更好玩，请直接指出“这是负资产设计”。

最终报告不要温和总结，要做真正有判断力的结论。
