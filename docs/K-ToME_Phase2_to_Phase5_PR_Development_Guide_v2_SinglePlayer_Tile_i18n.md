
# K-ToME 后续阶段完整开发文档（Phase 2 ~ Phase 5，PR 级执行版，单机 / 中文优先 / Tile 重构版）

> 版本：v2-rebuild  
> 状态：Draft for direct implementation  
> 适用范围：Phase 2 ~ Phase 5  
> 本版定位：**直接替换**此前所有与下列新约束冲突的 Phase 2 ~ Phase 5 规划。

## 0. 本版修订摘要

本版文档不是对旧版后续规划做局部修补，而是做一次**硬约束驱动的重排与重构**。以下规则从本版开始视为不可被破坏的产品约束：

- **纯单机，唯一玩家**：当前范围内不考虑联机、共斗、同步、旁观、队友目标、队友复活、多人解谜、多人门槛。
- **不允许纯辅助职业**：每个职业都必须具备单通能力，必须自带输出、自保、位移/脱困、Boss 处理路径。
- **Phase 2 即引入 i18n**：中文为默认首选语言；首页提供切换到英文的按钮；进入游戏后当前 session 内不可切换；所有 UI、日志、技能、装备、怪物、任务与教程必须一键切换。
- **Phase 2 即废弃 ASCII**：从正式开发路径中移除 ASCII 模式；正式渲染、地图、任务、装备、技能、怪物、UI 都转入 Tile-first 设计。
- **资源流水线前置**：从 Phase 2 起，美术和音频不再是“最后补齐的表现层”，而是系统设计的一部分；所有正式图片资源通过离线 Gemini 图像流水线生成、处理和入库。
- **中土系高幻想风格**：风格参考《指环王/魔戒》系“古典、中土、旧石材、锻铁、木梁、火炬、雾、史诗高幻想”气质，但不直接复刻任何受版权保护的角色脸、徽章、镜头构图或专名。

## 2. 全局硬约束（Phase 2 起统一生效）

### 2.1 产品范围冻结

- 只做**单机单人 run**。
- 不做任何依赖第二个玩家、队友单位或网络同步的玩法。
- 不允许“需要队友才成立”的职业、技能、道具、任务或地图机关。
- 不做在线排行榜、云存档、账号系统；若后续要做，也只能在当前架构之外另起范围。
- 当前版本允许本地 Profile、成就、运行记录、局部回放，但都必须是**本地单机数据**。

### 2.2 职业单通合同（Solo-Clear Contract）

一个职业只有同时满足以下六项，才算可进入正式版本：

1. 有明确主输出路径（持续或爆发皆可）。
2. 有自保路径（护盾、格挡、再生、净化、躲闪、减伤、转移等至少一条）。
3. 有位移、脱困或站位修正能力。
4. 有群体处理方案。
5. 有 Boss 处理方案。
6. 有糟糕局面的 panic answer（逃脱、短时无敌、拉开、强回复、控制窗口等）。

以下设计**一律禁止**：

- 主要功能是给队友加血/加 Buff，自身无完整伤害闭环。
- 核心技能只能对友方施放，不能自施或不能转化为单机有效收益。
- 伤害循环必须建立在“队友先上某种状态”上。
- 必须有人替你控场、破甲或挡刀，职业本身才成立。

### 2.3 中文优先的 i18n 合同

- `zh-CN` 是默认语言，也是主稿语言。
- `en-US` 是唯一强制第二语言。
- 语言切换只出现在**首页**；进入 `GameScreen` 后当前 session 内不可切换。
- 所有正式玩家可见文本必须使用稳定 key：`nameKey`、`descKey`、`uiKey`、`logKey`、`loreKey`、`statusKey`。
- **禁止**在正式 YAML、core、client 里直接写裸中文/英文作为玩家可见文案。
- 动态数值说明必须走模板渲染，不允许把文字烘焙进图片。

### 2.4 Tile-first 合同

- Phase 2 开始，正式路径不再提供 ASCII 可玩模式。
- `core` 仍然零引擎依赖，但必须输出足够完整的语义展示快照，供 Tile/UI/Audio 消费。
- 所有正式内容都必须有 `visualKey`，大多数交互内容还必须有 `audioProfile`。
- 地图、机关、任务物件、技能范围、地表危险区都要以 Tile/Overlay/特效形式被表达；不接受“靠日志脑补地图”的旧方案。
- 所有 Boss 高危险技能必须有清晰可读的 Tile telegraph。

### 2.5 资源流水线合同

- 图片资源的生成发生在**离线开发流水线**，不是游戏运行时。
- 运行时只消费已 cook 好的 atlas、manifest 与音频 cue。
- 所有正式图片资源必须能追溯到：
  - `AssetSpec`
  - Prompt 模板版本
  - 原始输出（raw）
  - 处理脚本
  - 最终 atlas/manifest
- 音频也必须经过统一处理流水线，不允许后期到处散落匿名文件。
- 任何“先随手塞张图，之后再说”的提交都视为技术债，不允许进主干。

### 2.6 质量与验证合同

每个 PR 都必须同时给出：

- 范围与非目标。
- 自动化验证命令。
- 固定 seed 或固定场景的白盒验收步骤。
- 与 i18n/visual/audio 相关的覆盖声明。
- 对 saveVersion、ProfileVersion、AssetManifestVersion 的影响说明（若有）。

## 3. Phase 2 以后统一架构

### 3.1 模块拓扑建议

```text
root
├── core/                 # 纯 Kotlin，零引擎依赖
├── game/                 # 数据、注册表、内容拼装
├── client/               # libGDX 渲染、输入、音频、屏幕与 orchestration
├── tools/
│   ├── asset-pipeline/   # Gemini 图像生成 + 图片处理 + atlas 打包
│   ├── audio-pipeline/   # 音频规范化、转码、cue manifest 生成
│   ├── locale-lint/      # key 覆盖、占位符一致性、术语检查
│   ├── content-lint/     # visual/audio/i18n/数据 schema 检查
│   └── smoke/            # headless smoke / golden seed / golden screenshot
├── assets-src/           # raw 图、处理图、prompt、style bible、音频母带
└── docs/
```

### 3.2 core / game / client 的边界

**core 必须负责**：

- Entity / Component / System
- Turn Scheduler
- Combat Resolver
- Stats / Formula
- Status / Talent / Item / Loot
- Map / ProcGen / FOV / LOS
- AI Decision / Behavior
- Save DTO / Event DTO
- 语义事件与日志 token

**core 禁止负责**：

- 纹理、字体、音频句柄、屏幕跳转、按钮状态
- 任何 libGDX 类型
- 任何本地化字符串拼接结果
- 任何 atlas region 解析

**game 必须负责**：

- YAML/JSON 内容装载
- registry 装配
- ContentId 到逻辑定义的映射
- 官方内容包
- 未来 mod overlay 的落点

**client 必须负责**：

- TileRenderer
- UI、输入、屏幕切换
- Locale bundle 装载与文案渲染
- atlas / icon / VFX / Audio cue 解析
- 玩家可见日志呈现
- golden screenshot 测试入口

### 3.3 共享数据合同

推荐所有正式内容对象至少具备如下字段：

| 字段 | 含义 | 备注 |
| --- | --- | --- |
| `id` | 稳定内容 ID | 只允许 ASCII 标识，不允许本地化文本 |
| `nameKey` | 名称 key | 双语言必备 |
| `descKey` | 描述 key | 双语言必备 |
| `visualKey` | 主视觉 key | 无则不能进入正式内容 |
| `iconKey` | 图标 key | UI/背包/技能树使用 |
| `audioProfile` | 音频档案 | 映射到多个 cue group |
| `logProfile` | 日志档案 | 映射到事件 key 与参数 |
| `tags` | 检索标签 | 构筑、掉落、AI、Quest 等使用 |
| `telegraph` | 目标预警定义 | 技能/陷阱/Boss 必备 |
| `loreKey` | Lore 文本 | 高价值内容强制要求 |

推荐日志事件结构：

```kotlin
data class LogTokenEvent(
    val eventId: String,
    val localeKey: String,
    val args: Map<String, String>,
    val turn: Int,
    val category: LogCategory
)
```

推荐渲染快照结构：

```kotlin
data class RenderSnapshot(
    val mapCells: List<CellView>,
    val props: List<PropView>,
    val actors: List<ActorView>,
    val overlays: List<OverlayView>,
    val floatTexts: List<FloatTextView>,
    val uiState: UiStateView,
    val logEvents: List<LogTokenEvent>
)
```

### 3.4 语言切换规则（必须统一）

- 首页切语言后，新的 `sessionLocale` 写入即将进入的 session。
- 局内不允许改 `sessionLocale`。
- 存档不存“最终文本”，只存 ID 与 token；因此回到首页切语言再进入同一存档时，可以按当前首页语言重新渲染。
- 若以后要改成“存档绑定语言”，必须整体修改合同；本版不这么做。

### 3.5 覆盖率与静态门禁（Phase 2 起）

推荐从 Phase 2 起建立如下强制门禁：

- `./gradlew test`
- `./gradlew jacocoTestReport`
- `./gradlew :core:jacocoTestCoverageVerification`
- `./gradlew :tools:locale-lint`
- `./gradlew :tools:content-lint`
- `./gradlew :tools:asset-lint`
- `./gradlew :tools:audio-lint`
- `./gradlew :tools:smoke:headless`
- `./gradlew :client:goldenScreens`

额外硬门禁：

- 所有正式内容 `i18n` 覆盖率 100%。
- 所有正式内容 `visualKey` 覆盖率 100%。
- 所有正式内容 `audioProfile` 覆盖率必须达到设计声明要求；若某内容故意静音，也要显式标注。
- `core` 关键包覆盖率维持在 85% 左右；整体不得低于 80%。

## 4. 资源流水线（全阶段共用）

### 4.1 图像流水线：离线生成，不进运行时

图像流水线固定为：

```text
AssetSpec
 -> PromptCompiler
 -> Gemini provider
 -> raw image store
 -> segmentation / crop / pivot / normalize
 -> outline / shadow / palette pass
 -> atlas pack
 -> visual manifest emit
 -> client runtime resolve
```

关键原则：

- **Gemini 负责生成源图，不直接当最终运行时小图**。
- 先产大图/母图，再程序化切图、裁边、校色、缩放、打包。
- Tile 时代真正的可读性来自：轮廓、占格、对比、危险色，而不是纯生成质量。
- 尽量避免在资源图里烘焙可变文字。技能名、状态名、说明都由运行时字体绘制。
- Phase 2 ~ 3 的角色与怪物动画以**静态主体 + 程序化动效**为主；真正重型逐帧动画只在高价值 VFX 上少量使用。

### 4.2 音频流水线：规范化与路由优先

音频流水线固定为：

```text
source wav / synth / sample
 -> trim / normalize / loop-check / transcode
 -> cue manifest
 -> runtime routing
 -> bus mix / ducking / priority
```

关键原则：

- 先定义 cue 分类，再补文件。
- 所有重要反馈事件都必须有唯一可识别音色，不允许不同重要事件共用同一廉价 cue。
- 不做大规模语音配音，优先把 SFX、ambience、music 做稳。
- 所有音频都必须能从 `audioProfile` 回溯到 cue 组。

### 4.3 美术风格总则（中土气质，不做 IP 复刻）

风格锚点：

- 古典高幻想
- 历史感、磨损感、石材、铁器、木梁、羊皮纸
- 冷暖对比：火炬橙、月光蓝、苔藓绿、熔铁红
- 严肃、沉稳、史诗，不做夸张二次元或卡通化

红线：

- 不直接生成“电影某角色的脸”“某部电影海报构图”“具体徽记”“具体专名”。
- 只保留氛围、材质语言和世界气质。

### 4.4 资源评审清单（每个资源 PR 必须回答）

- 这个资源的 `AssetSpec` 在哪里？
- Prompt 版本是什么？
- raw 图保存在何处？
- 处理脚本或处理步骤是什么？
- 最终 `visualKey` / `audioProfile` 是什么？
- 它属于哪个 biome / 职业 / 稀有度 / 事件主题？
- 中英文 UI 下是否都可读？

## 5. Phase 2 — 单机基线重构（Tile + i18n + 资源流水线前置）（v0.2.0）

### 5.1 体验合同

- 玩家从中文首页进入游戏，可在首页一键切到英文；进入游戏后语言锁定到本次 session，局内不可切换。
- 正式可玩版本彻底抛弃 ASCII；地图、怪物、装备、技能、任务物件、UI、日志都以 Tile/图标/特效/音频呈现。
- 存在 4 个可单通的基础职业，玩家可完整跑通一条 2~4 小时的单机短局。
- 所有正式内容都具备双语言、视觉键值、音频键值与可追溯的资源来源。

### 5.2 本阶段冻结决策

- 单机唯一玩家视角冻结：不做队友目标、组队 Buff、共斗解谜、复活同伴、联机同步。
- 中文为默认首选语言；英文是唯一强制第二语言；语言切换只允许在首页进行。
- Phase 2 开始正式弃用 ASCII；`AsciiRenderer` 不再是可玩模式。
- Tile 作者规格冻结为 64x64 主资产，桌面默认 48x48 运行时显示；不做等角投影，保留正交网格读图优势。
- 所有图片资源必须通过离线 `AssetGenerationProvider -> Gemini -> processing -> atlas` 流水线进入项目；运行时禁止联网生成。
- 所有职业都必须具备单通能力；任何纯辅助/纯治疗职业方案在本版范围内一律废弃。

### 5.3 非目标

- 不做逐帧重动画和复杂剧情演出。
- 不做世界级长局内容填充，只做 2~4 小时单机闭环。
- 不做联网生成资源；Gemini 只在离线工具链里用。

### 5.4 内容与资源预算

| 类别 | 最低交付 | 说明 |
| --- | --- | --- |
| 职业 | 4 个基础职业 | 战卫、奥术师、游荡者、圣堂武士 |
| 天赋 | 48 个 | 每职业 12 个，3 树 x 4 |
| 种族 | 1 个默认可玩 | 先只做人类骨架，Phase 3 再扩 |
| Zone | 4 个 | 3 个常规 + 1 个 Boss 终局 |
| 怪物模板 | 48 个 | 36 普通/8 精英模板/4 Boss |
| 装备与消耗品 | 42 个基础条目 | 12 武器基底/10 防具/12 消耗品/8 饰品或 Unique |
| 地形与道具 Tile | >= 240 个 | 地表、墙体、门、箱、机关、任务物件 |
| 角色/怪物图 | >= 64 个 | 含头像与检视图 |
| 技能/状态/物品 Icon | >= 180 个 | 技能、状态、任务、装备 |
| VFX 套件 | >= 30 套 | 范围提示、投射物、命中特效、地表危险 |
| SFX | >= 90 条 | UI、脚步、战斗、机关、怪物、掉落 |
| BGM/Ambience | 4 首 BGM + 8 条环境循环 | 标题、探索、Boss、胜利/失败 |

### 5.5 美术计划

- 先做 Style Bible，再做资产，不允许先出图再倒推风格。
- 视觉风格锚点：古典高幻想、中土系史诗感、旧石材/锻铁/木梁/苔藓/火炬/雾；禁止卡通、高饱和霓虹、现代 UI 符号。
- Phase 2 只交付静态主体 + 程序化微动效，不做重度逐帧角色动画。
- 所有正式资源必须可追溯到 `AssetSpec`、prompt 版本、raw 图、处理脚本和 atlas manifest。

### 5.6 音频计划

- 先建立 cue 分类和总线，再补资源；不允许后面靠文件名猜用途。
- 重点补齐：UI、脚步、近战、施法、受击、开门、拾取、升级、任务推进、Boss 预警。
- 环境层从 zone 设计开始绑定，不能等地图做完后再补。

### 5.7 i18n 计划

- 中文文案为主稿；英文必须同步可用。
- 新内容 PR 没有双语言 key 不允许进主干。
- 所有动态说明走模板，不在图片里烘焙任何文字。

### 5.8 PR 拆分

### P2-PR01 — 确定性调度、事件总线与语义日志 V2

**目标**

把 Phase 1 的基础回合循环升级为可本地化、可回放、可做 Tile/VFX/SFX 驱动的事件流；任何玩家可见日志都不得再由 core 直接拼接字符串。

**依赖**

Phase 1 全部完成。

**主要改动**

- 把行动结果统一收敛为 `GameEvent` / `CombatEvent` / `QuestEvent` 三类语义事件；事件只携带稳定 ID、参数与时间戳，不携带已渲染文案。
- 调度器升级为 1000 能量制，队列排序键固定为 `energy desc -> initiative desc -> entityId asc`，保证跨机器确定性。
- 在 core 引入 Hook/Callback 总线，支持 `onAct`、`onMove`、`onHit`、`onDamageTaken`、`onKill`、`onQuestStepChanged` 等基础节点。
- 日志系统改为 `LogEventKey + Args`，运行时由 client 根据当前 session locale 渲染文本；存档中保存事件 token 而不是已拼好的中文/英文句子。
- 所有 VFX/SFX 触发改为监听语义事件，不允许 gameplay 代码直接调 client。

**自动化验证**

- 固定 seed 下，同一套输入脚本在两次运行中产生完全一致的事件序列哈希。
- 同一战斗事件在 `zh-CN` 与 `en-US` 下渲染文本不同，但事件参数、数值与顺序完全一致。
- 回调总线单测覆盖注册、注销、优先级顺序、异常隔离与 re-entrant 安全性。

**白盒验收**

- 固定 seed 开局，玩家连打 20 回合，比较 `events.jsonl` 哈希必须稳定。

**合并门禁**

### P2-PR02 — i18n V1：中文默认、首页切英文、局内锁定

**目标**

建立中文优先、英文必达的本地化基线；从这一 PR 起所有玩家可见文本必须走 key，不允许任何新增裸字符串进入正式路径。

**依赖**

P2-PR01。

**主要改动**

**合并门禁**

### P2-PR03 — RenderSnapshot、VisualKey、AudioKey 合同落地

**目标**

建立 core 到 client 的正式展示契约，让 Tile、VFX、SFX、UI 都通过稳定 key 解析，彻底斩断 ASCII 时代的 glyph 依赖。

**依赖**

P2-PR01, P2-PR02。

**主要改动**

- 新增 `RenderSnapshot`：包含地块层、道具层、角色层、遮罩层、指示器层、浮字层、UI 面板数据，但不包含具体纹理对象。
- 内容对象统一增加 `visualKey`、`iconKey`、`vfxProfile`、`audioProfile`、`inspectPortraitKey` 等字段。
- 建立 `VisualManifest` 与 `AudioManifest`，由 client 在启动时装载并校验 key 完整性。
- core 只负责输出 `telegraph shape / actor facing / highlight state / fog state / ui state` 这类语义信息，渲染细节由 client 决定。
- 删除正式路径中的 `AsciiRenderer` 与 glyph atlas；若保留调试功能，只允许存在 grid debug overlay，不得作为可玩模式。

**自动化验证**

- Manifest 解析测试：所有 shipped content 的 `visualKey`、`audioKey`、`iconKey` 必须可解析。
- 客户端 smoke：空地图、战斗、开箱、拾取、升级四类 snapshot 都能正确落地。

**白盒验收**

- 打开检视面板，怪物名/描述/头像/技能图标/掉落图标都来自 key 解析，而不是硬编码。

**合并门禁**

正式内容对 glyph 的直接依赖为 0；缺失 visual/audio key 的 content 不能合并。

### P2-PR04 — TileRenderer 基线：图集、分层、雾遮罩与程序化微动效

**目标**

P2-PR03。

**主要改动**

- 动效原则冻结：Phase 2 只做静态主体 + 程序化位移/闪白/缩放/粒子，不做逐帧大动画，避免把资源线拖死。

**自动化验证**

**合并门禁**

### P2-PR05 — 图像资源流水线 V1：Gemini 生成、程序处理、图集打包

**目标**

把‘所有图片走 Gemini’变成离线、可回放、可审计的开发流水线，而不是把线上模型调用混进游戏运行时。

**依赖**

P2-PR03, P2-PR04。

**主要改动**

- 新增 `tools/asset-pipeline`，定义 `AssetSpec`、`PromptTemplate`、`StyleBible`、`VariantPolicy`、`CookManifest`。
- 图像生成后端固定先实现 `GeminiFlashImagePreviewProvider`，模型名使用用户指定的 `gemini-3.1-flash-image-preview`；同时定义 `AssetGenerationProvider` 接口，预留后续替换空间。
- 流水线步骤固定为：`spec -> prompt compile -> Gemini raw output -> background/mask extract -> crop/pivot -> palette/contrast normalize -> tile safe area check -> atlas pack -> manifest emit`。
- 原始图、处理脚本、产出图、manifest 全部入版本管理或对象存储，禁止只留最终小图、丢掉来源。
- 建立版权与风格红线：只参考‘中土气质的古典高幻想’，禁止直接复刻电影角色脸、徽章、海报构图与专名。

**自动化验证**

- `asset-lint`：分辨率、透明边、占用面积、命名、manifest 一致性检查。
- `atlas-build`：重复构建结果稳定，region 名不漂移。
- `prompt-manifest-test`：同一 spec 可回放到同一 raw 资产集合，不要求模型本身 determinism，但要求流水线 determinism。

**白盒验收**

- 新增一个狼怪物资产时，开发者只需补 `AssetSpec`，跑脚本即可得到 raw 图、处理图、atlas entry 与 visual manifest。
- 查看仓库时能追溯每张正式小图的 prompt 版本、raw 来源与处理链。

**合并门禁**

运行时禁止直连 Gemini；正式包只带 cooked assets。

### P2-PR06 — 音频流水线 V1：Cue、分层、规范化与运行时路由

**目标**

## 6. Phase 3 — 深层战斗、职业扩容与世界分支（v0.3.0）

### 6.1 体验合同

- 游戏从短局原型扩展为 6~10 小时的完整单机 run，构筑差异明显。
- 基础职业扩到正式树，种族与进阶职业加入，Boss 战全面依赖 telegraph 与 Tile 读图。
- 世界地图与分支 zone 成型，掉落和构筑开始真正驱动玩法。
- 资源与本地化继续同步扩容，不允许系统深度领先于表现层。

### 6.2 本阶段冻结决策

- 冻结五个种族与四个进阶职业范围，防止职业树无限膨胀。
- 冻结 6 条基础伤害通道与 Power/Save 对抗模型。
- Boss 大伤害技能必须有图形 + 日志 + 音频三重预警。
- 世界地图仍然只服务单机单人流程，不引入队伍共享任务或多人门槛。

### 6.3 非目标

- 不做完整 mod SDK 冻结，mod 仍留到 Phase 4。
- 不做云档、排行榜或账号系统。
- 不为了多样性而引入无法单通的职业。

### 6.4 内容与资源预算

| 类别 | 最低交付 | 说明 |
| --- | --- | --- |
| 基础职业 | 4 个正式化 | 每职业扩到至少 24 天赋 |

| 新增 SFX/BGM | >= 120 条 SFX / 7 首音乐 | 含 Boss、世界地图、进阶职业 |

### 6.5 美术计划

- 重点转向‘职业辨识度’与‘Biome 辨识度’，而不只是量的堆砌。
- Boss、种族、进阶职业都要有独立头像、轮廓和特效语言。
- 所有新增职业树必须在 icon 语言上可区分，不允许套模板乱改色。

### 6.6 音频计划

- 扩到战斗层级反馈：阶段切换、Boss 蓄力、狂暴、净化、稀有掉落。
- 不同职业/种族要有自己的施法或武器反馈族谱。

### 6.7 i18n 计划

- 建立术语表与关键词注册表，避免同机制多种翻译。
- Boss、种族、职业说明做第一次语言 QA 清盘。

### 6.8 PR 拆分

### P3-PR01 — 战斗公式 V2：非线性属性、伤害通道、Power/Save 对抗

**目标**

把 Phase 2 的可玩战斗升级到可长期扩展的数值骨架，解决后期线性堆属性崩盘问题。

**依赖**

v0.2.0。

**主要改动**

- 冻结核心对抗维度：`Accuracy vs Defense`、`Physical/Mental/Spell Power vs Saves`、`Crit Chance vs Crit Resist`、`Armor/Resistance/Penetration`。
- 把主要生存与命中属性改为边际收益递减曲线；面板显示 Raw 值，同时在战斗内部换算 Effective 值。
- 建立 6 条基础伤害通道：物理、火焰、寒冷、闪电、神圣、暗蚀；所有技能、怪物、装备、地形危害都必须显式标注。
- 统一暴击、穿透、格挡、护盾、减伤层级的结算顺序，生成可打印的 `CombatTrace` 供白盒验算。
- 对描述模板暴露统一数值 API，保证中文/英文说明能实时读取同一公式结果。

**自动化验证**

- 针对命中、暴击、护甲、抗性、豁免的公式金样本单测。
- 同一角色堆高单一属性时，收益曲线必须符合预期，不出现无限接近 100% 不死或必中。
- 双语言描述快照：技能说明数值与 `CombatTrace` 对得上。

**白盒验收**

- 用高防战卫和高闪避游荡者分别对同一精英测试，结果能明显体现不同防御机制，而不是同一条血条硬扛。

**合并门禁**

所有核心公式必须进入 `CombatTrace` 回归；禁止把新公式写死在 UI 描述里。

### P3-PR02 — 状态、持续、铭文与回调系统 V2

**目标**

把控制、增益、持续伤害、持续技能和铭文系统做成真正数据驱动的基础设施。

**依赖**

P3-PR01。

**主要改动**

- 状态系统分为 `buff / debuff / sustain / delayed / zone effect` 五类，统一生命周期接口。
- 持续技能（Sustain）引入显式激活/停用、维护成本、冲突组和 UI 状态图标。
- 铭文系统正式进入：治疗、位移、防护、净化四大类，全部自洽于单机单人玩法，不依赖队友。
- 所有状态都必须具备 `statusKey`、`iconKey`、`vfxProfile`、`audioProfile` 与 `callback hooks`。
- 建立 dispel、cleanse、stun immunity、silence、pin 等关键控制互动的优先级规则。

**自动化验证**

- 状态叠加/刷新/互斥/净化/免疫单测。
- 铭文冷却、资源约束、使用时机回归测试。
- 持续技能开关对面板、日志、SFX、状态图标的联动测试。

**白盒验收**

- 在一场战斗里同时触发流血、燃烧、护盾、净化、短距位移，UI 与日志必须能完整解释。

**合并门禁**

新增状态没有图标、localized key、回调注册与清理逻辑的一律拒绝。

### P3-PR03 — 天赋树框架 V2：数据驱动、断点成长、动态说明

**目标**

让天赋系统具备 ToME 级可扩展性，同时让文案、图标、VFX/SFX 与机制同源。

**依赖**

P3-PR01, P3-PR02。

**主要改动**

- 天赋定义固定为数据文件 + 解析器 + 执行器；字段至少包含 `tier`、`maxPoints`、`requirements`、`cooldown`、`cost`、`targeting`、`telegraph`、`breakpoints`。
- 动态说明统一走公式模板，升级前后差异可在 UI 中预览。
- 建立 `TalentKeywordRegistry`，让流血、护盾、格挡、潜行、引雷等关键词可跳转机制解释。
- 天赋 target shape 标准化：单体、线、锥形、半径、地表持续区、自己为中心六种；全部映射到 Tile telegraph。
- 洗点与回滚逻辑必须能正确撤销被动与持续技能的数值修饰。

**自动化验证**

- 天赋解析与 schema 单测。
- 断点成长测试：1/3/5 点等关键节点必须出现正确机制变化。
- 说明文案渲染测试：升级前后数值与标签变化正确。

**白盒验收**

- 在技能树里预览某技能从 2 点升到 3 点，应能直观看到范围或附加效果的质变说明，而不是只涨数字。

**合并门禁**

所有可释放天赋必须声明 telegraph 与 targeting；无描述模板的天赋不能进入正式内容。

### P3-PR04 — 基础职业扩容到正式树，并建立 SoloClearLab

**目标**

把 Phase 2 的四个职业从可玩原型扩展到能支撑整局构筑的正式职业。

**依赖**

P3-PR01 ~ P3-PR03。

**主要改动**

- 每个基础职业扩到至少 24 个天赋（6 树 x 4），并明确主动/被动/持续三类比例。
- 每个职业必须具备至少两条互相区分的通关构筑路径，不允许只有一个标准答案。

- 战卫强调控制与格挡，奥术师强调屏障与元素轮转，游荡者强调潜行与位移爆发，圣堂武士强调惩击与自我神圣维持。

- 技能树完整性扫描：无孤儿节点、无死前置、无未翻译说明。
- 职业热键栏和 HUD 状态联动测试。

**白盒验收**

- 任选一个职业，都能做出至少一种偏生存和一种偏爆发的打法，而且都能打穿 Phase 3 主线。

**合并门禁**

职业树缺少 Boss answer 或 panic answer 的，视为未完成。

P3-PR04。

### P3-PR09 — Boss 脚本、Telegraph 语法与遭遇战规范

**自动化验证**

- `headless-smoke:p3`、`balance-lab:p3`、`locale-lint`、`asset-lint`、`save-migration` 全绿。
- 至少 8 组职业/种族人工通关验证。
- Profile 与 Save 多版本升级回归。

**白盒验收**

- 任一语言、任一基础职业或已解锁进阶职业，都能完成 Phase 3 主线，不需要借助多人机制。

**合并门禁**

Phase 3 的主线体验长度、稳定性、职业可通关性全部达标后再进入 Phase 4。


### 6.9 出口标准

- 至少 8 套职业/种族组合完成人工通关验证。
- Boss 战 telegraph、构筑差异和掉落驱动都已经成立。
- 世界地图与分支任务能稳定读档恢复。
- 双语言在完整长局中无明显术语漂移与 UI 爆版。

## 7. Phase 4 — 程序生成深水区、装备生态与 Mod SDK（v0.4.0）

### 7.1 体验合同

- 世界探索变得更不可预测：隐藏区、事件、随机神器、随机首领、复杂门禁共同形成中后期张力。
- 掉落系统从构筑强化升级为构筑驱动核心。
- Mod 作者可以安全地扩展数据、脚本、文本、Tile 和音频资源。
- 项目从‘一个游戏’进一步变成‘一个可扩展的单机 roguelike 平台’。

### 7.2 本阶段冻结决策

- 冻结混合拓扑地图生成方案与 Pattern/Vault 数据格式。
- 冻结 Affix/Rarity/Artifact/Randart 基本语义与预算模型。
- 冻结 Mod Manifest、Overlay、Lua Hook API V1 和资源命名空间规则。
- Mod 仍以单机本地为前提，不考虑联网同步。

### 7.3 非目标

- 不做联机 mod 分发平台。
- 不把 AI 最终性能打磨放到本阶段解决；这里只做系统接口与内容扩容。
- 不为了随机而牺牲可解释性。

### 7.4 内容与资源预算

| 类别 | 最低交付 | 说明 |
| --- | --- | --- |
| 新增高级 Zone/隐藏区 | >= 8 个 | 含隐藏区和事件型区域 |
| Pattern/Vault 模板 | >= 40 个 | 机关室、宝库、祭坛、剧情房 |
| 怪物模板总量 | >= 200 个 | 含变异精英与随机首领素材 |
| Affix | >= 80 条 | 前缀/后缀/主题效果 |
| Unique/Artifact/Randart | >= 60 个高价值条目 | 手工 + 程序混合 |
| 新增 Tile/Props | >= 400 个 | 高级 biome、隐藏区、Artifact 表现 |
| 新增 Icon/VFX | >= 250 个 | 高价值掉落、首领、事件 |
| 新增 SFX/BGM | >= 140 条 SFX / 5 首音乐 | 隐藏区、Artifact、事件、首领 |

### 7.5 美术计划

- 重点在稀有度层次、隐藏区风格差异和高价值掉落的视觉回报。
- Pattern/Vault 必须先有空间概念图再出最终 Tile。

### 7.6 音频计划

- 隐藏区、Artifact 掉落、事件触发、随机首领必须拥有与普通内容明显区分的声音轮廓。

### 7.7 i18n 计划

- Mod 资源中文优先；官方 SDK 文档中英双语至少覆盖最小上手路径。
- Lore 和隐藏事件文本开始大量增加，术语审校继续跟进。

### 7.8 PR 拆分

### P4-PR01 — 混合拓扑地图生成 V3：房间、环路、图案模板

**目标**

把 Zone 从‘能生成’升级到‘每次都值得探索’，并为任务、隐藏区、Boss 房预留空间语法。

**依赖**

v0.3.0。

**主要改动**

- 生成器升级为 `rooms + corridors + loops + pattern vaults` 混合架构，替换过于单调的 BSP-only 方案。
- 图案模板（Pattern/Vault）成为正式数据资产，支持固定布局的大房间、机关室、宝库、祭坛区、Boss 前厅。
- 生成阶段必须感知大型 prop、Boss arena、任务物件和可交互结构，避免后补时互相打架。
- 保留 deterministic seed，可导出生成调试图、连通图和危险度热力图。
- 世界地图与 zone 元数据支持多套生成 profile。

**自动化验证**

- 1000 seed 批量生成连通性测试。
- Pattern/Vault 放置合法性与重叠冲突测试。
- 危险度和奖励分布统计测试。

**白盒验收**

- 玩家在同一 biome 连刷 10 次，也不该总是看到同一类走廊和房间组合。

**合并门禁**

生成器任何一次产出不可达主线、Boss 房缺失、关键道具堵死都算阻塞。

### P4-PR02 — 锁钥匙、任务拓扑与可解性验证

**目标**

让更复杂的任务和地图门禁在程序生成条件下仍然数学上可解。

**依赖**

P4-PR01。

**主要改动**

- 把门、封印、祭坛、机关、钥匙、任务道具抽象为拓扑节点，先在抽象图层完成可解性校验，再落地到地图。
- 支持主线门禁、可选奖励门禁、一次性捷径和回环开启四类结构。
- 任务生成器要能声明‘某钥匙必须早于某封印可达’这样的硬约束。
- 失败时生成器必须重掷，不允许把死局交给玩家。
- 所有关键门禁必须有清晰视觉和音频反馈。

**自动化验证**

- DAG/可解性校验单测。
- 随机任务门禁 500 seed 回归。
- 世界内 marker 与任务日志同步测试。

**白盒验收**

- 拿到矿坑升降机齿轮前，升降机应清晰处于不可用状态；拿到后重新检视和接近时反馈完整变化。

**合并门禁**

任何程序生成任务死局都必须在 CI 中能被固定 seed 重现。

### P4-PR03 — 掉落生成 V3：iLvl/qLvl/词缀预算与稀有度层

**目标**

把掉落系统推进到可长期扩容的 Diablo/ToME 式装备学，而不是手写一堆例外表。

**依赖**

P3-PR10。

**主要改动**

- 引入 `item level`, `quality level`, `affix tier`, `rarity budget`, `treasure class` 五层控制参数。
- 词缀池支持类型限制、互斥组、权重、层级、最小区域等级、职业标签和主题标签。
- 稀有度扩到普通/魔法/稀有/神器四层；Unique 与 Randart 在此基础上独立分流。
- 生成器输出 `LootTrace`，方便白盒验证某件装备为什么能或不能掉。
- UI 需支持展示词缀来源、主题和范围，不要求把所有底层数字都暴露给普通玩家。

**自动化验证**

- 词缀过滤、权重抽样、互斥组测试。
- 区域等级与掉落合法性批量统计。
- `LootTrace` 快照回归。

**白盒验收**

- 低级区不会掉终局神器；高级区掉出的普通物品也不会全是垃圾到不可看。

**合并门禁**

任何新增 affix 必须带 icon 标签、双语言名称、机制说明与平衡预算。

### P4-PR04 — Unique、Artifact 与 Randart 流水线

**目标**

建立高价值战利品层，拉开普通随机装与传奇战利品之间的体验差距。

**依赖**

P4-PR03。

**主要改动**

- 定义三类高价值物品：手工 Unique、手工 Artifact、程序 Randart。
- Randart 规则固定为：基底强化 + 主题词缀 + 特殊被动/触发能力；不得只是数值更大。
- 所有高价值物品必须拥有专属 icon、掉落光效、拾取提示音、检视边框与 lore 文案。
- 建立 `ArtifactThemeRegistry`，让火焰、古树、矮人工匠、亡者秘仪等主题能映射到表现与词缀。
- 对高价值物品增加日志高亮与死亡掉落提示。

**自动化验证**

- Randart 生成合法性和预算测试。
- 主题表现完整性检查：visual/audio/text 三件套齐全。
- Unique/Artifact 掉落频率统计。

**白盒验收**

- 玩家一眼就能看出‘这是普通稀有装’还是‘这是会改变构筑的高价值物品’。

**合并门禁**

高价值物品没有独立表现和 lore 的，一律不算完成。

### P4-PR05 — 精英突变体与随机首领系统

**目标**

利用程序生成扩展中后期敌人多样性，避免内容穷尽后战斗变平。

**依赖**

P4-PR03, P4-PR04。

**主要改动**

- 建立 `EliteMutation` 与 `RandBossTemplate` 两层系统：前者轻量增强普通怪，后者混合职业/词缀/技能生成首领级怪物。
- 随机首领生成必须绑定主题、危险提示、奖励表和死亡日志，不允许只偷偷抬数值。
- 首领的随机技能组合要受禁配表约束，避免不可读或绝对无解组合。
- 为随机首领生成专属名字规则、头像边框、环境音和战斗音乐切换。
- 扩展怪物检视，能解释精英/首领的关键机制。

**自动化验证**

- 随机首领组合合法性与禁配表测试。
- 精英词缀表现映射测试。
- 奖励与危险度预算统计。

**白盒验收**

- 遇到随机首领时，玩家应该先通过检视和 telegraph 读懂危险，再决定打还是撤，而不是被一发不知名技能蒸发。

**合并门禁**

任何随机首领都必须有可解释名字、可解释危险提示和可解释奖励。

### P4-PR06 — 隐藏 Zone、世界事件与探索奖励层

**目标**

把世界探索从‘刷主线图’扩展成有秘密、有风险、有超额回报的真正冒险结构。

**依赖**

P4-PR01, P4-PR02, P4-PR05。

**主要改动**

- 新增隐藏入口、世界事件、特殊商旅/祭坛/追猎事件、局部剧情遭遇。
- 探索奖励层要覆盖额外掉落、永久增益、支线 lore、快捷通路或特殊首领。
- 所有隐藏区都必须在 Tile 与音频上明显区别于普通地图，强化发现感。
- 事件系统支持概率、条件、冷却、互斥和一次性奖励。
- 任务日志与世界地图要能记录已发现/未完成/已关闭的支线机会。

**自动化验证**

- 事件触发条件与互斥测试。
- 隐藏入口可达性和关闭状态测试。
- 奖励重复刷取防重测试。

**白盒验收**

- 玩家第一次发现古墓暗门时，应同时获得视觉、音频与日志三重反馈。

**合并门禁**

隐藏内容不能靠像素猎奇；必须有系统级的发现线索。

### P4-PR07 — Mod Manifest、依赖解析与 Registry Overlay

**目标**

把项目最初的 mod-first 承诺兑现到正式可用层级，但仍保持单机本地优先。

**依赖**

v0.3.0，最好在 P4-PR03 之后。

**主要改动**

- 定义 `mod.yaml`：id、name、version、author、dependencies、conflicts、loadOrder、entryPoints、assetPacks。
- 实现 Registry Overlay：mod 可追加或覆盖职业、种族、怪物、物品、zone、文本、visual/audio manifest。
- 加载顺序固定：`core game -> official content -> enabled mods -> user override`。
- mod 仅针对单机本地运行，不做联机校验、服务器权威或同步问题。
- TitleScreen 增加 Mod 列表与启用/禁用界面，但不与语言切换耦合。

**自动化验证**

- 依赖/冲突/加载顺序解析测试。
- overlay merge 结果快照测试。
- Mod 开关后存档兼容告警测试。

**白盒验收**

- 启用一个新增怪物与物品的小 mod 后，标题页可见、游戏内可掉落、双语言和 Tile 表现正常。

**合并门禁**

mod 系统仍然是单机本地功能；不预埋多人同步字段。

### P4-PR08 — Lua Runtime Host、Sandbox 与 Hook API V1

**目标**

给 mod 和高层玩法逻辑开放脚本扩展能力，同时把边界和安全沙箱先立住。

**依赖**

P4-PR07。

**主要改动**

- 脚本运行时仅暴露白名单 API：查询实体、修改状态、注册回调、创建效果、读数据定义，不直接暴露底层文件系统和线程。
- Hook API V1 至少覆盖：战斗、移动、施法、死亡、任务推进、掉落生成、地图生成后处理。
- 脚本错误必须可捕获、可定位、可禁用，不允许直接把客户端带崩。
- 提供脚本层 localized text 与 visual/audio key 访问方式，但仍要求最终资源在 manifest 中注册。
- 文档化官方示例：新增技能、改掉落、改 AI、加 zone 事件。

**自动化验证**

- Lua 沙箱权限测试。
- 脚本报错隔离测试。
- Hook 注册/触发/卸载测试。

**白盒验收**

- 写一个 50 行以内的脚本，为战卫增加一个受击后回怒的被动，游戏内可直接验证。

**合并门禁**

任何可破坏沙箱或直接越过 manifest 的脚本入口都不允许。

### P4-PR09 — Mod 资源管线：i18n/Tile/Audio Override 与打包规范

**目标**

让 mod 不只是改数字，而是真能安全扩展文本、图像、音频与 UI 资源。

**依赖**

P4-PR07, P4-PR08。

**主要改动**

- 定义 mod 资源目录规范：`i18n/`, `visuals/`, `audio/`, `assets-src/`, `scripts/`。
- mod 允许通过自己的 `AssetSpec` 走同一套 Gemini 图像流水线，最终产出私有 atlas 与 manifest。
- mod 的 i18n 资源必须至少提供中文；英文可以可选，但若 mod 声称支持英文则必须通过 lint。
- 运行时对 mod atlas、音频 cue 与 base game 资源进行命名空间隔离，避免 key 冲突。
- 增加 mod 资源 lint 与打包任务。

**自动化验证**

- mod atlas 构建与命名空间冲突测试。
- mod i18n key 覆盖测试。
- 禁用 mod 后资源卸载与回滚测试。

**白盒验收**

- 安装一个只加新怪和新区域资源的小 mod，主游戏资源不应被误替换或串音。

**合并门禁**

mod 资源同样要走可追溯流水线，不允许往包体里直接扔匿名 png/ogg。

### P4-PR10 — 官方示例 Mod、总转换骨架与 SDK 文档

**目标**

降低外部内容作者上手成本，让 mod-first 不停留在口号。

**依赖**

P4-PR07 ~ P4-PR09。

**主要改动**

- 提供三个官方示例：新增职业、改掉落规则、追加小型隐藏区。
- 提供 `total-conversion` 骨架，展示如何替换主菜单、文本 bundle、视觉和音频清单。
- SDK 文档至少覆盖 manifest、数据 schema、Lua API、资源流水线、测试任务、常见坑。
- 示例内容也必须是单机单人可玩的，不引入组队依赖。
- 为示例 mod 配置 headless smoke。

**自动化验证**

- 示例 mod 都能在 CI 中构建通过。
- SDK 文档中的最小示例可运行。
- total conversion 骨架能替换标题页与一小段开局流程。

**白盒验收**

- 新开发者按文档 30 分钟内能做出一个新装备或新怪物，并在游戏里看到对应 Tile 和说明。

**合并门禁**

示例与文档不同步时，以失败处理。

### P4-PR11 — Phase 4 资源扩充：高级 Biome、Artifact 套装、首领视听强化

**目标**

为更深的生成与掉落系统补足足够多的资源母体，避免随机系统在表现上重复。

**依赖**

P4-PR01 ~ P4-PR10。

**主要改动**

- 新增高级 biome 资源包、隐藏区专属布景、Artifact 专属 icon 和掉落特效、随机首领边框与头像套件。
- 音频新增高级环境层、特殊机关音、Artifact 掉落 cue、世界事件 cue。
- 更新 style bible，确保资源扩容后仍保持中土系高幻想统一气质。
- 强化 inspect 与 lore 页面，支撑 Unique/Artifact/隐藏事件的叙事承载。
- 清理 Phase 2/3 中质量不达标的旧图旧音频。

**自动化验证**

- 新资源覆盖率与 atlas/audio 打包回归。
- Artifact/首领专属视听绑定检查。
- 资源风格审查清单执行。

**白盒验收**

- 高级隐藏区的视觉和听觉应该让玩家立刻知道‘这里不是普通分支图’。

**合并门禁**

随机系统扩容后的资源重复度不得明显回升。

### P4-PR12 — Save/Mod 兼容、Headless Mod Harness 与 v0.4.0 封版

**目标**

把世界深度与 mod SDK 一起收口成可长期迭代的平台版本。

**依赖**

P4-PR01 ~ P4-PR11。

**主要改动**

- saveVersion 升到 4，引入 mod 指纹、启用列表、资源版本、脚本 API 版本。
- 为 mod 构建 headless harness：可加载 mod、跑地图生成、战斗、掉落和脚本 smoke。
- 加载带不同 mod 集合的存档时给出明确兼容提示与阻断策略。
- 封板前冻结 manifest 与 Hook API V1，不再随意改签名。
- 产出 v0.4.0 SDK 包、示例仓、已知限制列表。

**自动化验证**

- `headless-mod-smoke`、`save-mod-compat`、`overlay-regression` 全绿。
- 无 mod、单 mod、多 mod 三种配置人工验证。
- 脚本错误恢复与禁用流程测试。

**白盒验收**

- 玩家在标题页禁用某个大 mod 后，游戏应明确告诉他哪些存档不可用，而不是静默损坏。

**合并门禁**

Mod API 未冻结前，不进入 Phase 5。


### 7.9 出口标准

- 高级 procgen、掉落系统和随机首领都可解释、可回归、可追踪。
- 官方示例 mod 能在 SDK 文档指导下独立跑通。
- 世界事件和隐藏区不再像手工硬塞，而是成为流程自然部分。

## 8. Phase 5 — 战术 AI、性能稳定与发布级打磨（v0.5.0）

### 8.1 体验合同

- 敌人具备明确战术意图，潜行、仇恨、Boss 选位与场地利用都更成熟。
- 游戏在长局、群战和低配配置下都能稳定运行。
- 玩家可查看本地 run history、死因分析和局部回放，形成单机复盘闭环。
- 内容、资源、语言、SDK、安装包一起达到可发布层级。

### 8.2 本阶段冻结决策

- 冻结 AI 的 Utility + Behavior Tree 双层架构。
- 冻结最终 FOV/LOS 方案与性能分析指标。
- 冻结难度层、本地回放/历史记录格式和发布材料格式。
- 明确不做联网账号、在线排行榜、云存档。

### 8.3 非目标

- 不扩展新大系统，只做 AI、性能、发布级打磨和收口。
- 不新增联网服务。
- 不把 Gold 版本变成继续堆内容的垃圾场。

### 8.4 内容与资源预算

| 类别 | 最低交付 | 说明 |
| --- | --- | --- |
| AI Archetype | >= 10 类 | 近战、远程、施法、潜行、召唤、首领等 |
| 最终怪物行为包 | >= 40 套 | 按族群与首领拆分 |
| 最终资源修订 | 全量清盘 | 补齐缺口、替换劣质资源 |
| 新增 SFX/BGM | >= 120 条 SFX / 4 首音乐 | 最终混音、阶段切换、死亡回放 |
| 本地化 QA | 100% 正式内容 | 中英双语全流程验证 |

### 8.5 美术计划

- 清理最后一轮风格不统一、可读性不足或占位性质资源。
- 确保危险区、Boss 技能、稀有掉落的可读性高于纯好看。

### 8.6 音频计划

- 把混音、优先级、ducking、环境层切换做稳，形成发布级听感。

### 8.7 i18n 计划

- 完成全流程双语言 QA，包括安装包文档、死因分析、回放界面和 SDK 文档。

### 8.8 PR 拆分

### P5-PR01 — Utility AI 评分框架

**目标**

把敌人从简单状态机升级为会衡量距离、血线、地形、技能窗口和目标威胁的战术决策体。

**依赖**

v0.4.0。

**主要改动**

- 建立 `Consideration`、`UtilityAction`、`ScoreContext`、`DecisionProfile` 四个核心抽象。
- 评分输入至少包含：玩家距离、自己血线、资源、冷却、地表危险、目标威胁、目标脆弱度、自己职责标签。
- 支持近战压迫、远程拉扯、残局收割、召唤控场、逃离治疗、守点等行为意图。
- AI 决策必须可打印 `AIDecisionTrace`，便于回放和调试。
- 先不追求学术花哨，只做 deterministic + 可解释。

**自动化验证**

- 评分函数金样本测试。
- 同一输入下 `AIDecisionTrace` 稳定性测试。
- 极端场景（低血、近身、技能冷却、场地危险）决策合理性测试。

**白盒验收**

- 远程法系在残血且技能未好时，应优先拉开并寻找掩体，而不是继续站桩。

**合并门禁**

AI 决策必须可解释；无法导出 trace 的行为不允许进正式怪物。

### P5-PR02 — 行为树执行层与战术动作编排

**目标**

把‘决定做什么’和‘具体怎么做’拆开，让复杂敌人流程仍然可维护。

**依赖**

P5-PR01。

**主要改动**

- 建立行为树节点：选择器、顺序器、条件、动作、装饰器、冷却门、重试门。
- 效用 AI 只负责选高层意图，行为树负责寻路、选位、开技能、撤退、喝药、追击等具体步骤。
- 支持 AI 技能前摇、蓄力、telegraph、取消、逃跑路径与掩体搜索。
- 为不同怪物族群配置模板树：近战、远程、施法者、首领、召唤者、潜行者。
- 保留 Phase 4 的脚本 Hook，让 mod 能扩展行为节点。

**自动化验证**

- 行为树节点组合测试。
- 寻路 + 掩体 + 技能序列集成测试。
- AI 取消与重规划测试。

**白盒验收**

- 首领在准备大招前应先找合适站位、给出 telegraph，再施放，而不是无脑贴脸原地放。

**合并门禁**

所有高危险技能都必须能被 AI 正确 telegraph 与执行。

### P5-PR03 — 仇恨焦点、潜行与战术感知系统

**目标**

让潜行、仇恨与目标切换从作弊式全知全能，升级为更公平也更有压迫感的战术系统。

**依赖**

P5-PR01, P5-PR02。

**主要改动**

- 敌人不再直接读取玩家绝对坐标，而是通过视野、噪音、伤害来源、最后已知位置生成 `HateFocus`。
- 潜行变为属性对抗：潜行值、感知值、噪音事件、光照与地形共同决定暴露概率。
- 引入‘搜寻’、‘怀疑’、‘追踪’、‘失去目标’四段感知状态。
- 高智能敌人允许做包夹、堵门、压制危险地块；低智能敌人仍保持更直白的追击模式。
- 日志与检视要能解释敌人为什么锁定你或失去你。

**自动化验证**

- 潜行暴露概率与视野状态测试。
- HateFocus 生命周期测试。
- 多怪物感知同步与分歧测试。

**白盒验收**

- 游荡者从阴影里打一刀后，敌人应该扑向最后已知位置，而不是瞬移般追踪当前格子。

**合并门禁**

潜行玩法必须可解释、可反制、可学习。

### P5-PR04 — FOV/LOS 最终算法、缓存与可视化打磨

**目标**

在可读性优先的前提下，把视野、视线和地形遮挡性能做稳。

**依赖**

P2-PR04。

**主要改动**

- 对比并最终冻结 FOV/LOS 算法；推荐使用优化射线追踪或等价的高可读方案，并引入 dirty flag 缓存。
- 只有玩家位置、关键遮挡变化、视野半径变化时才重算整图 FOV。
- 半透明、门缝、拐角、窄缝可见性要在算法与表现层一起调平。
- 检视模式加入‘为什么看得见/看不见’调试覆盖层，仅在 debug 可见。
- 保证 AI 感知与玩家视觉使用兼容但可区分的规则层。

**自动化验证**

- 视野金样本图回归。
- 门开关、爆破破墙、位移后的缓存失效测试。
- 宽图和狭长图性能对比测试。

**白盒验收**

- 玩家在门口斜角站位时，不会出现一格完全不讲理的盲区。

**合并门禁**

FOV 结果必须同时通过可读性检查与性能门禁。

### P5-PR05 — 渲染/内存性能整治：Atlas、Pooling、剔除与 Profiling

**目标**

把中后期大混战、技能特效和大量日志浮字下的性能风险系统性压下去。

**依赖**

P2-PR04, P3-PR11, P4-PR11。

**主要改动**

- 正式启用 `GLProfiler` 和运行时性能 HUD（debug only），跟踪 Draw Call、Texture Binding、对象池命中率、GC 峰值。
- 高频对象（浮字、临时 VFX、路径节点、CombatTrace 片段）全面接入对象池。
- 按层拆 atlas，减少纹理切换；对超视口或不可见实体启用剔除与动画停更。
- 地表残留特效、环境粒子与 UI 飘字都必须有预算上限和降级策略。
- 建立低配 preset：低分辨率、降粒子、低阴影、简化环境动效。

**自动化验证**

- 性能基准场景对比测试。
- 对象池泄漏与复用测试。
- 低配 preset 功能回归。

**白盒验收**

- 在 20+ 怪物、多个地表危险区和连续技能释放的场景中，客户端不会出现肉眼可见卡死。

**合并门禁**

必须有可追踪的性能基线；优化不能靠体感。

### P5-PR06 — 音频运行时打磨：混音层、环境层与音乐切换

**目标**

把已有音频资源真正用起来，形成稳定、辨识度高且不吵的最终听感。

**依赖**

P2-PR06, P3-PR11, P4-PR11。

**主要改动**

- 建立音乐状态机：标题页、探索、警戒、Boss、胜利、死亡六类场景。
- 环境音分层：底噪、局部事件、机关脉冲、天气；允许随 zone 与战斗状态淡入淡出。
- 关键反馈（暴击、升级、任务完成、Artifact 掉落、Boss 预警）优先级高于普通战斗噪声。
- 提供总线级音量设置与静音选项，但局内不暴露语言切换。
- 处理叠音上限与 ducking，避免混战时糊成一团。

**自动化验证**

- 音乐状态切换测试。
- 高并发音效场景下的句柄与优先级测试。
- 音量设置持久化测试。

**白盒验收**

- Boss 开战、血线阶段切换、Artifact 掉落，玩家闭眼都能听出重要事件发生。

**合并门禁**

重要反馈事件不得被普通脚步或小技能声淹没。

### P5-PR07 — UI 最终打磨、可访问性与本地化 QA

**目标**

让最终版本在信息密度高的前提下仍然可读、可学、可维护。

**依赖**

P2-PR07, P3-PR12。

**主要改动**

- 重做热键栏、状态栏、对比面板、技能树、检视窗的视觉层级与留白。
- 提供色弱安全方案、字号缩放、日志过滤、战斗数字开关、危险地块高对比模式。
- 进行中英双语言的全流程文案 QA，统一术语并清理歧义。
- 增加教程提示、首领危险提示与死亡后总结的本地化文本。
- 把所有调试占位图、测试文案、未完成标签清盘。

**自动化验证**

- UI 回归截图测试。
- 可访问性选项持久化与即时生效测试。
- 双语言术语审计。

**白盒验收**

- 不开开发者模式，玩家也能在复杂战斗里读懂自己为什么中毒、为什么减速、Boss 下一步要做什么。

**合并门禁**

release 包中不允许存在 TODO 文案、占位图标或未翻译文本。

### P5-PR08 — 难度阶梯、Run History、死因分析与局部回放（本地）

**目标**

给单机玩家提供复盘与长期挑战动力，但不引入任何多人依赖。

**依赖**

P2-PR11, P3-PR12, P5-PR01。

**主要改动**

- 难度至少分为正常、困难、噩梦三档，均为单机本地数据，不做在线排行。
- Run History 记录角色、职业、种族、种子、死亡层、死因、关键装备、关键技能、总回合数。
- 死因分析基于语义事件与 CombatTrace，可回看最后 50~100 回合关键事件。
- 局部回放仅做战斗/位置/事件重播，不做全局网络同步或多人观战。
- 标题页增加运行记录入口。

**自动化验证**

- Run History 读写与分页测试。
- 死因归因与局部回放完整性测试。
- 难度参数切换回归。

**白盒验收**

- 玩家死亡后能看出自己是被哪一击、哪种状态、哪次错误站位带走，而不是只看到‘你死了’。

**合并门禁**

所有历史与回放数据都必须建立在本地单机存档上，不引入服务器。

### P5-PR09 — 最终内容补齐：Tile、VFX、SFX、Lore、双语言清盘

**目标**

P5-PR05, P5-PR06, P5-PR07。

**主要改动**

- Lore 页面、物品传说、Boss 简介、区域介绍全部补双语言。
- 清理重复度高或质量不达标的旧资源；同主题资产统一轮廓与色彩规则。
- 音频补齐剩余环境层、精英/首领专属 cue、界面操作反馈。
- 执行最终 style bible 审核。

**自动化验证**

- 全量资源覆盖率扫描。
- 语音/音效/图像 manifest 完整性测试。
- 双语言 final smoke。

**白盒验收**

- 随便开一局，从首页到通关，不应再看到明显的资源断层。

**合并门禁**

内容缺口在 release 前必须归零。

### P5-PR10 — 性能回归矩阵与低端机/长局稳定性验证

**目标**

把‘能跑’升级为‘跑得稳、跑得久、不同配置都可接受’。

**依赖**

P5-PR05。

**主要改动**

- 建立性能回归矩阵：开局、普通战、中期群战、Boss、隐藏区、特效峰值六类基准场景。
- 增加长局 soak test：连续运行数小时，验证内存、句柄、日志、存档和对象池不会劣化。
- 建立低端配置 smoke：缩放、低特效、低音频并发下可完整通关。
- 把崩溃报告、断言、关键 trace 输出整理成发布前质量门禁。
- 对 Android/桌面（若两端都做）分别记录差异，但不引入平台功能分叉。

**自动化验证**

- 自动性能基准测试。
- 长局 soak test。
- 低端 preset 全流程人工验证。

**白盒验收**

- 默认配置和低配配置都能完成一整局，不会越玩越卡。

**合并门禁**

没有性能基线图和 soak test 结果，不得出 gold。

### P5-PR11 — 打包、安装包验证、Mod SDK 发布材料与用户文档

**目标**

P4-PR12, P5-PR07, P5-PR09。

- 校验安装包瘦身、首启时间、资源完整性与缺失文件保护。
- 不做联网账号、排行榜、云存档。

**自动化验证**

- 安装包 smoke。
- 首启与存档路径测试。
- SDK 文档引用示例回归。

**白盒验收**

- 不看源代码的新玩家能安装、切语言、开始游戏、存档读档；内容作者能照文档做最小 mod。

**合并门禁**

文档与安装包不一致视为阻塞缺陷。

### P5-PR12 — Gold Master 封版与发布后 backlog 冻结

**目标**

形成真正可发布的 v0.5.0，并把后续版本入口整理清楚。

**依赖**

P5-PR01 ~ P5-PR11。

**主要改动**

- 归档性能基线、语言 QA 结果、资源版本、SDK 版本与 saveVersion。
- 发布 v0.5.0。

**自动化验证**

- 全量 CI 绿灯。
- 最终人工回归 checklist 全通过。
- 发布包哈希与版本元数据归档。

**白盒验收**

- 从首页切语言到完整跑一局、查看死因、装一个官方示例 mod，全流程都不再需要临时修修补补。

**合并门禁**

达不到 gold checklist，不得贴 release 标签。


### 8.9 出口标准

- 完整长局、低配、长时间 soak、双语言回归全部达标。
- 无联网依赖下，玩家可完成安装、切语言、通关、复盘、装示例 mod 全流程。
- 发布材料、SDK 文档和安装包已经收口。


## 9. 跨阶段长期保留的回归矩阵

### 9.1 Golden Seed 回归

| 套件 | 从哪个阶段开始 | 目的 |
| --- | --- | --- |
| `GoldenSeed-P2` | Phase 2 | 验证 Tile、i18n、基础职业、短局主线闭环 |
| `GoldenSeed-P3` | Phase 3 | 验证职业/种族/世界地图/Boss/掉落 |
| `GoldenSeed-P4` | Phase 4 | 验证高级 procgen、隐藏区、Artifact、随机首领 |
| `GoldenSeed-P5` | Phase 5 | 验证 AI、性能、难度、死因分析与发布包 |

规则：

- 每套 Golden Seed 都要固定输入脚本、固定期望结果和固定证据位置。
- Golden Seed 一旦进入主干，只能增加，不能随意替换。
- 对于影响数值的大 PR，允许更新期望结果，但必须解释为什么变。

### 9.2 Locale 回归

每次 release 前必须验证以下页面在 `zh-CN` / `en-US` 下均成立：

- 标题页
- 角色创建
- HUD
- 背包 / 装备对比
- 技能树
- 怪物检视
- 任务日志
- 死因分析 / 回放（Phase 5）
- Mod 列表与 SDK 文档入口（Phase 4+）

### 9.3 资源覆盖率回归

每次 content freeze 前都要跑：

- 所有正式内容 `nameKey/descKey` 覆盖率 100%
- 所有正式内容 `visualKey` 覆盖率 100%
- 所有正式内容 `iconKey` 覆盖率 100%
- 所有必须出声的内容 `audioProfile` 覆盖率 100%
- 所有 atlas region / audio cue 都能被运行时解析

### 9.4 SoloClearLab 回归

每个可玩职业必须保留一组固定回归：

- 杂兵群测试
- 精英测试
- Boss 测试
- 资源枯竭测试

## 11. 推荐的 PR 模板（所有阶段通用）

```md
## 背景
本 PR 解决什么问题，属于哪个 Phase，依赖什么。

这一 PR 合并后，玩家或开发链路具体能得到什么。

列出会改动的模块、数据、资源、工具链。
```

## 12. 最终结论

这版后续规划的核心不是“把系统堆更多”，而是先把**单机可通关、中文优先、Tile 正式化、资源流水线前置**这四条主线锁死，再让后面的深系统、世界扩容、mod SDK、AI 与性能优化都建立在这四条主线之上。

因此，新的阶段顺序已经固定为：

1. **Phase 2**：先把 Tile、i18n、资源流水线、四个可单通职业和短局闭环做实。
2. **Phase 3**：在这个正式基线之上扩深战斗、职业、种族、世界分支和 Boss 设计。
3. **Phase 4**：再把程序生成、装备生态、随机首领和 mod SDK 放大成平台能力。
4. **Phase 5**：最后收口到战术 AI、性能稳定、发布级 polish、本地复盘与正式交付。

只要按本文件执行，后续 PR 的设计边界、资源接入规则、语言规则、阶段目标和验收口径就都是清楚的，开发不会再在“先做玩法还是先做表现”“要不要保留 ASCII”“本地化什么时候补”“职业能不能只做辅助”这些问题上来回摇摆。

## 附录：外部依赖注意事项（仅补充资源流水线约束）

- `gemini-3.1-flash-image-preview` 目前是 Google 官方公开的图像生成模型名，本文件按该模型设计图像资源流水线。
- 由于该模型当前属于 preview / pre-GA 形态，资源生成必须封装在 `AssetGenerationProvider` 之后，并且仅用于**离线开发流水线**，不能做成运行时硬依赖。
- 即便模型支持更好的 i18n 文本生成，也**不要把游戏文本烘焙进图像**；所有正式文本仍应由运行时字体系统绘制。
